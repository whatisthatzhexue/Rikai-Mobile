# LexiCandy 项目协作规范与开发协议（v1.0）

> 状态：当前权威（协作规范）｜最后同步：2026-11-14

**致团队成员：**

LexiCandy（释书糖）是一个**本地优先、证据可追溯、可定制的多语深读与写作工作台**。名字取“像吃糖一样轻松啃下原版书”之意；产品目标不是做一个翻译器，而是围绕“阅读—写作—社区”的闭环，让用户在看懂原版书的同时发出自己的声音。

当前仓库的代码基线来自 Rikai 阶段：可运行的离线日语阅读、OCR、分词、MDict 查词与可选 Agent 已经存在；LexiCandy 阶段的写作页、社区页、个人页、Supabase 用户数据、Python Worker、语言插件体系等，多数仍是规划或部分实现。**协作时必须区分“当前可运行”与“转型目标”，不得把规划写成已支持。**

本文只规定**协作流程**：分工、分支、提交、评审、验证、沟通与文档沉淀。产品、隐私、架构、UI、文档治理的硬规则仍以 [`项目规则`](项目规则.md) 的 `R-*` 为唯一来源；本文与规则冲突时，以规则文件为准，并修正本文。

------

## 〇、适用对象与规则边界

- 适用于所有参与 LexiCandy 的开发者、文档维护者、设计与测试人员，以及使用 AI 辅助工具的人。
- 当前项目可能由单人维护，也可能由多人协作；下文角色可以由同一人兼任，但**兼任时仍要显式切换视角**：写代码的人、评审的人、发布的人不能互相替代责任。
- 本文的“须/不得”是协作流程要求，不新增产品规则；涉及产品范围、隐私、架构、UI、Agent 的硬约束，一律引用 [`项目规则`](项目规则.md) 的 `R-*`。
- 当前项目定位以 [`LexiCandy 阶段原始需求`](../04-历史/原始需求/LexiCandy阶段/) 为准；`Rikai阶段/` 是上一阶段归档，不再作为新功能依据。

## 一、项目架构与目录权责

### 1. 目标架构

| 层 | 技术 | 职责 | 明确不做 |
|---|---|---|---|
| 客户端 | Flutter（当前 Android 单端） | 阅读/写作/社区/个人四页；本地 OCR、分词、MDict 查词、Agent 编排、语言插件宿主 | 不把核心推理放到云端；不把图片、路径、Key 发给模型 |
| 用户数据与社区 | Supabase | 用户鉴权、社区内容、术语表同步、必要的用户数据 | 不碰核心 OCR/分词/查词推理；不保存用户 API Key |
| 调度端 | Python Worker | 轻量调度、可选云端 OCR（转型项）、Prompt/规则/配置分发、脱敏遥测与 Bad Case 聚类 | 不接触、不代理用户 LLM Key；云端 OCR 只处理用户明确提交的图片，不留存/不训练；不做未披露的数据收集 |
| 语言插件 | Dart 接口 + 规则文件 | 分词器、查词策略、OCR 语言路由、Prompt 模板、标注规则 | 核心不得写满某语种特判的 if-else |
| 本地数据 | 分词器/MDict/模型 | 当前：用户自备、原地读取、运行时下载或导入；目标：可增加服务端 UniDic/预置词典（需许可与规则修订） | 当前不入库、不复制用户目录、不上传；任何预置/服务端数据先过许可与 ADR |

**端云边界：** 本地 OCR、分词、查词必须在离线状态可用；Supabase 与 Worker 是可选增强，不是核心功能的前置条件。用户未配置 provider/API Key、未主动发送请求时，不应联网。

> 当前仓库**尚未创建** `supabase/`、`worker/`、语言插件目录。落地前先写 ADR，不要先建空目录、假接口或把规划路径写进代码依赖。

### 2. 当前仓库结构

```text
Rikai-Mobile/                  # 仓库根目录；产品名 LexiCandy
├── android/                   # Android 宿主、Kotlin、Manifest、资源
├── assets/                    # 模型清单、字体说明、图标、许可
├── docs/                      # 规范/设计/进度/历史/参考/样本/维护
├── integration_test/          # 真机/模拟器集成测试
├── lib/                       # Flutter 源码
│   ├── core/                  # 纯模型、主题、通用 UI、工具
│   ├── services/              # OCR/MeCab/MDict/Agent/存储/查词
│   ├── state/                 # Riverpod provider/controller
│   └── features/              # 页面与 widget
├── packages/                  # 本地 path 包：rikai_ocr、mecab_for_dart
├── test/                      # 单元/widget 测试
├── third_party/               # 第三方许可/来源说明
├── tool/                      # 文档检查、验证、MDict spike
├── supabase/                  # 规划：迁移、Edge Functions、配置（尚未创建）
├── worker/                    # 规划：Python Worker（尚未创建）
└── plugins/                   # 规划：语言插件（尚未创建）
```

- `lib/core` 不依赖 `services/state/features`；`lib/services` 不导入 `features/state`，也不依赖 Flutter UI；`lib/state` 可依赖 core/services；`lib/features` 可依赖 core/state/services。
- 所有全局 provider 放在 `lib/state/`，不要在 `features/` 新建全局 provider。
- Agent prompt 只在 `lib/services/agent/agent_prompts.dart`；查词逻辑由 `LookupGateway` 共享，UI 与 Agent 不复制查词选择/排序。
- `packages/rikai_ocr`、`packages/mecab_for_dart` 是本地 path 包；`rikai_ocr` 的包名与 `RikaiOcr` 类名是当前兼容契约，未经 ADR/迁移验证不要改名。

### 3. 分工权责

| 角色 | 主要负责 | 交付物 | 不负责 |
|---|---|---|---|
| 客户端/Flutter | 四页 UI、状态、路由、本地管线、插件宿主、输入法 | 页面、组件、状态、测试 | Supabase schema、Worker 算法 |
| 云端/Supabase | 鉴权、RLS、社区、术语表、迁移 | migrations、RLS、Edge Functions、配置 | 核心 OCR/分词/查词 |
| Worker/算法 | 调度、云 OCR、配置分发、遥测、Bad Case | Worker 服务、任务、数据管道 | 用户 LLM Key、核心推理；云端 OCR 不留存原图 |
| 语言插件/规则 | 分词/查词/OCR/Prompt/标注规则文件 | 插件包、规则、测试 | 其他语言的核心 if-else |
| 文档/质量 | 规则/数据/设计/进度/历史/维护；验证 | 文档、检查脚本、测试报告 | 代替 owner 做技术决策 |

- 跨模块改动必须在 Issue/PR 说明原因、影响面、回滚方案，并请对应 owner review；没有 owner 的模块默认由客户端负责人代管。
- 新增模块先指定 owner，再写代码；不要留下“大家都管、实际没人管”的目录。
- 角色可以兼任，但**代码作者不能同时作为唯一评审人**；单人维护时至少执行 §六 的自审清单并保留验证记录。

### 4. 模块边界

- `core`：跨 feature 的纯模型、设计 token、通用工具；不放业务页面。
- `services`：OCR、MeCab、MDict、Agent、存储、查词等能力实现；通过窄接口/Port 暴露，不直接依赖 UI。
- `state`：Riverpod provider/controller；集中管理应用级状态。
- `features`：页面与交互；只做展示和用户操作，不复制底层能力。
- 新增语言能力优先走插件/规则文件；核心只保留通用编排，不把日语假设扩散到共享层。

## 二、Git 工作流规范

### 1. 分支定义

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 稳定、可发布 | 多人协作时受保护；禁止直接 push；必须 PR + 验证 |
| `dev` | 集成分支 | 多人协作启动时创建；功能分支合入此处 |
| `feat/<name>/<topic>` | 新功能 | 从 `dev` 拉出；一个分支一个目标 |
| `fix/<name>/<topic>` | Bug 修复 | 从 `dev` 拉出；线上紧急问题走 hotfix |
| `docs/<name>/<topic>` | 文档 | 可只改 `docs/`；仍须通过文档检查 |
| `chore/<name>/<topic>` | 构建、依赖、工具 | 不混功能改动 |
| `hotfix/<version>-<topic>` | 线上紧急修复 | 从 `main` 拉出；合回 `main` 与 `dev` |

- 当前如果只有一名活跃开发者，小步改动可以在 `main` 上提交；但涉及 OCR、隐私、数据库、依赖、发布、架构的改动，仍必须开分支并自审。
- 多人协作启动后启用 `dev` 与 PR 保护；`main`/`dev` 禁止 force push、禁止删除、禁止绕过 review。
- 分支名使用英文小写、数字、连字符；`<name>` 用拼音；不要用中文、空格、全角标点。
- 不 rebase 别人的分支，不重写已推送的共享历史；需要整理时在自己的功能分支内完成。

### 2. 标准动作

1. **同步**：`git fetch origin`，再 `git pull --rebase origin dev`（或 `main`）。
2. **建分支**：`git switch -c feat/zhangsan/reader-bubble-tabs origin/dev`。
3. **开发**：小步提交；每完成一个可验证单元就跑相关测试。
4. **自检**：`dart tool/verify.dart`；文档改动跑 `dart tool/check_docs.dart`；UI/OCR 变更按需做设备验证。
5. **提交**：按 §三 的格式；一个提交只做一件事。
6. **发起 PR**：目标 `dev`；写清变更、原因、验证、风险、关联 Issue。
7. **评审**：至少 1 名非作者 review；高风险改动 2 人；作者不能自批。
8. **合并**：默认 Squash merge；删除功能分支；保证 `dev` 可构建。
9. **发布**：按 §2.4 执行。

### 3. 评审规则

Review 重点：

- 逻辑正确性与边界条件；
- 离线核心是否仍可用，云端是否仍为可选；
- 隐私：是否违反 §4.3 的图片/Key 规则（Agent/LLM 请求无图片、路径、Key；云端 OCR 有披露与留存策略）；
- 证据：citation 是否来自真实查词，模型推断是否标注；
- 架构：是否跨层依赖、是否新增第二套运行时/词典格式/状态管理；
- UI：是否使用设计 token、是否支持 200% 字体与无障碍；
- 测试：是否有回归测试，是否只用 fake provider；
- 文档：是否登记、横幅、链接、版本标签正确；
- 构建：是否带入密钥、大文件、生成物。

约定：

- Review 不是风格之争；以 [`项目规则`](项目规则.md)、[`设计规范`](设计规范.md)、[`项目数据`](项目数据.md) 为准。
- 提出 blocking 意见必须说明原因/影响/建议；作者修改后回复“已处理”并重新请求 review。
- 工作日 24 小时内给出首次反馈；阻塞他人时优先 review。
- 紧急 hotfix 可先合并后补 review，但必须在 Issue 记录原因、风险和后续动作。

### 4. 版本、标签与发布

- App 版本唯一来源：`pubspec.yaml` 的 `version: MAJOR.MINOR.PATCH+BUILD`。
- Git tag：`vMAJOR.MINOR.PATCH`；build number 只增不减；不要用产品阶段代替版本号。
- 发布前：`dart tool/verify.dart --build`；release 签名按 R-DEV-05；先 `--config-only` 检查（R-DEV-06）。
- 发布说明：用户可见变更、已知问题、隐私/数据影响、升级注意事项。
- 回滚：优先回退到上一个 tag/构建；不要重写已发布历史；数据库迁移必须前向兼容，破坏性变更先备份并写 ADR。
- 产品阶段、工作包、反馈波次、优先级、维护阶段、重构步骤必须使用 [`版本命名`](../07-维护/版本命名.md) 的唯一写法，不要混用。

## 三、Commit 提交规范

### 1. 格式

```text
type(scope): subject

body（为什么改、改了什么、影响面）

footer（Refs/Closes/BREAKING CHANGE）
```

### 2. Type

| Type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档 |
| `refactor` | 重构，无行为变化 |
| `test` | 测试 |
| `perf` | 性能 |
| `build` | 构建系统 |
| `ci` | CI/自动化 |
| `chore` | 依赖、工具、杂项 |
| `revert` | 回滚 |

### 3. Scope

常用 scope：`app`、`reader`、`write`、`community`、`me`、`lookup`、`ocr`、`mecab`、`mdict`、`agent`、`storage`、`ui`、`android`、`worker`、`supabase`、`plugin`、`deps`、`docs`、`ci`、`release`。

### 4. Subject 与正文

- Subject 用中文，祈使句，≤ 50 字符，结尾不加句号。
- 不要只写“update”“fix”；说明改了什么、为什么。
- 一个提交只做一个逻辑变更；不要混格式化、重构、功能。
- 正文写“为什么”和“影响面”；破坏性变更必须在 footer 写 `BREAKING CHANGE:` 和迁移方式。
- 引用 Issue/规则：`Refs: #123, R-ARCH-13`；修复用 `Closes #123`。
- 提交信息不得包含 Key、用户数据、图片路径、真实请求体。

**示例：**

```text
feat(reader): 增加句子气泡的知识/读音/理解入口
fix(ocr): 修复竖排照片旋转后未重新检测的问题
refactor(plugin): 抽离日语查词策略
docs(规范): 新增 LexiCandy 协作规范
test(agent): 补充请求体不含图片/路径的断言
chore(deps): 升级 flutter_launcher_icons
```

### 5. 版本标签

提交信息中的阶段/工作包/反馈波次使用统一写法：

- 产品阶段：`阶段 N`；
- 工作包：`P6.x`、`P7.x`；
- 当前范围：`P6.8-lite`、`P7-lite`；完整规划：`P6.8（完整）`、`P7（完整）`；
- 设备反馈：`反馈波次 N`；
- 优先级：`优先级 高/中/低` 或 `批次 A/B/C`；
- 维护阶段：`M-1/M0/M1`；Agent 重构：`R1a–R4`。

不要使用旧的 P 级数字优先级写法，也不要在非设备反馈文档中裸写 `Wave` 加数字。

## 四、开发铁律

### 1. 本地优先，离线核心

- 核心阅读、本地 OCR、分词、查词必须离线可用；Agent 与云端能力是可选增强（R-PROD-02）。
- 不得启动即联网、后台自动上传，或让用户未主动发送的请求产生网络流量（R-PROD-03）。
- 任何让离线核心依赖网络的改动都应被拒绝；需要联网的功能必须有本地降级/明确错误。
- 当前规则 R-PROD-05 仍禁止云 OCR、云翻译、云 ASR、ML Kit；LexiCandy 目标中的云端 OCR 是转型项，落地前必须先修订规则并写 ADR，不能先写代码。

### 2. 证据可追溯

- 任何 AI 结论都必须能追溯到 OCR 文本、分词器、词典或用户原文；找不到依据时必须标注“模型推断”。
- citation 只由 orchestrator 发放，模型不能自造来源；严格模式无依据进 `unresolved`，宽松模式的补充必须独立标注（R-SEC-06、R-AGENT-05/07/08）。
- “万物皆可溯”：用户点击结论应能高亮原图或原句；当前未实现的入口不要写成已支持。
- 证据展示优先用结构化卡片/短引用，不要用大段无法追溯的文字。

### 3. 隐私与密钥

- Agent/LLM 请求永不包含图片、base64、EXIF、文件路径或文件名；图片默认只在本机 OCR（R-PROD-04、R-SEC-01）。云端 OCR 是独立的可选能力：只有用户明确选择、隐私协议披露、企业模式关闭时才可上传；上传内容仅用于本次 OCR，不得留存、训练或转作他用。
- API Key 只放 `flutter_secure_storage`/Android Keystore；禁止 SharedPreferences、SQLite、日志、URL、仓库（R-SEC-03）。
- Worker 永远不接触、不代理用户 Key；用户 Key 由手机直连模型厂商。
- 日志、错误、崩溃报告不得含 Key、完整请求体、图片路径（R-SEC-04）；用户可见错误必须是中文可读文案（R-SEC-07）。
- 遥测只能上报脱敏后的日活、失败率、词典未命中率、部分元数据；不得含内容、图片、Key、路径。上报范围必须在隐私协议中披露，并提供关闭/最小化选项。
- 企业模式：优先本地处理，不做云端 OCR，减少 Agent API，保证数据隐私。
- 仓库、CI、测试、示例中不得出现真实 Key；测试只用 fake provider（R-SEC-08）。

### 4. 端云边界

- **Flutter**：渲染、状态机、本地 OCR/词典/分词管线、插件宿主。
- **Supabase**：用户鉴权、社区内容、术语表同步、必要的用户数据；不承担核心推理。
- **Python Worker**：轻量调度、可选云端 OCR（转型项）、Prompt/规则/配置分发、脱敏遥测、Bad Case 聚类；不做模型代理，不接触用户 LLM Key。
- 接入 Supabase 时：所有用户表启用 RLS；service role key 只放服务端；客户端只用 anon key；迁移只前进，破坏性变更先备份并写 ADR。
- Worker 接口必须契约先行：版本化、错误可机器读取、返回 Action/OCR 结果/配置；不得回传 provider 原始 body。
- 云端配置必须有本地兜底；断网时 App 仍能完成核心阅读/查词。

### 5. 插件与语言规则

- 日语只是第一个落脚点，不是架构本身。日语的振假名/活用、英语的词根词缀/短语动词、法语的阴阳性、德语的格位变化，必须编码为**语言插件/规则文件**，不能塞进核心 if-else。
- Token 模型字段必须可空；缺失字段优雅降级，不要因为某语言没有该字段而崩溃。
- 语言相关能力至少包括：分词器、查词策略、OCR 请求语言、Prompt 模板、标注/读音规则。
- 新增语言 = 新增插件 + 规则文件 + 测试；核心只做通用编排，不为单语言 fork。
- 语言规则是文件，可版本化、可校验；无效/超限规则整体拒绝并保留上一有效版本。
- 共享 UI/state 不得硬编码日语假设；通过语言能力接口获取。

### 6. 产品边界

- **五条产品原则**：所见即所点（以 OCR 为中心，点击即可查词/解析）；万物皆可溯（AI 结论可回跳原图/原句）；软件变身（学习快照、自定义、一键回到上次场景）；个人成长（后台静默记录，按时间段分析）；零配置前台、极客后台（普通用户默认可用，高级配置藏在深层设置）。
- **不是翻译器**：我们承载用户的思考，做深读与写作，不做一键翻译。
- **不做应用外悬浮窗**：保持应用内沉浸式体验。
- **PDF 只做基本文字提取**：核心叙事中心与竞争力在外文图书 OCR，不要过度投入 PDF 版面还原。
- **MDict 单格式**：LexiCandy 阶段定位明确不再引入其他词典格式，保持词典设计一贯性；若确需引入，先做产品决策/ADR。
- **首次启动**：展示预存示例书与解析效果，引导用户拍下第一张实景照片；预存内容的分词结果应可离线查看。
- **阅读（Read）**：语境→句→词的细粒度；句子气泡包含知识/读音/理解三 Tab；批注、术语库、防剧透折叠、三级平面图按设计推进。
- **写作（Write）**：阅读/写作一键滑动切换并各自缓存；AI 差异教练按句子闭合触发；写作引子按“最近批注→最近的书→日常练习”生成；内置输入法不调用 Agent。
- **社区（Community）**：分享批注/术语表；敏感词库 + 举报 + AI 质检（Worker 使用开发者自有审核 Key，不接触用户 Key）；用户内容责任与版权声明；术语表防剧透折叠。
- **个人（About Me）**：成长曲线、学习快照、设置；后台静默记录，用户可划时间段分析。
- **教师端/企业模式**：教师端通过局域网把阅读数据重新排布到网页，不做机械画面投屏；企业模式本地优先。两者均为后续能力，未实现前不得写成已支持。
- **当前状态**：四页中只有部分 Read 能力有 Rikai 基线；Write、Community、About Me 的成长曲线、Supabase、Worker、语言插件多数仍是规划。文档和 UI 必须如实标注。

### 7. UI 与交互

- 所有页面使用 [`设计规范`](设计规范.md) 与 `lib/core/theme/app_tokens.dart`；不得硬编码颜色、字号、间距、圆角（R-UI-01）。
- 信息粒度按“语境→句→词”组织，拒绝信息过载；先给用户下一步操作，再给细节。
- 点击句子弹出读音与操作气泡；气泡固定“知识/读音/理解”三 Tab；知识优先本地词典，读音优先词典与分词器，理解优先结构分析，再按需询问 Agent。
- 段落“总结”给出若干语境相关备选项，用户点击后再展开；术语库创建走独立流程。
- 术语库支持文化梗/专有名词标记、即时生效、防剧透折叠。
- 三级平面图：第一层原书 OCR 重叠排版与无感翻页；第二层点击弹出本地 MDict 与分词结构；第三层句子关系、音调读法、可溯源 Agent 解析。
- 无障碍：Semantics、触控 ≥40dp、200% 字体、阅读放大镜；当前仅浅色主题（R-UI-12）。
- 空态/错误态必须给出下一步操作；错误文案引用固定文案表；不得出现全屏 loading、阻塞弹窗、无原因错误（R-UI-10/11）。

### 8. Agent 设计

- 被动式 Agent：用户触发，不主动打扰，不在用户不感兴趣的地方消耗预算。
- Agent 初期接用户配置的 LLM API；端侧小模型是后续选项，必须本地运行，并遵守同样的证据、隐私与预算规则。
- 降低决策成本：优先按钮/预制问题；与语境强相关的才由 Agent 生成；其余用 mock 预制问题兜底。
- 固定流水线，模型无工具、无自由 ReAct；orchestrator 预取 OCR/分词/逐词查词，模型只做理解、推断、引用已有证据（R-AGENT-01/03/04）。
- 模型不能改变模式、词典、provider、model，也不能执行代码（R-AGENT-11）。
- 能用“图 + 文”简易表达的，优先设计 schema/结构化卡片，不要让用户看大段文字。
- 没有分词器/词典依据时，必须标注模型推断；严格/宽松模式的证据规则见 R-AGENT-07。
- 图片永不进入模型；请求只能是文本 JSON（R-AGENT-12、R-SEC-01）。
- 预算/上限只引用统一常量；截断必须显式警告，不得静默丢弃（R-AGENT-LIMITS-001）。
- 所有 prompt 集中在 `agent_prompts.dart`；其他文件不得散落硬编码 prompt（R-AGENT-19）。
- Agent 输出质检样本按 [`样本说明`](../06-样本/说明.md) 存放；样本不得含图片、路径、Key 或真实用户数据。
- 自动化测试只用 fake provider；真实 provider/API Key/secure storage/arm64 Agent 必须人工验收（R-AGENT-17）。

### 9. 输入法

- 应用内输入法，不做应用外输入法；严格 App 沙盒，不影响系统输入法环境。
- 词典 + 分词器是权威信息源；输入法不调用 Agent。
- 最小支持 26 键布局；支持日语与中日模糊输入、罗马音/拼音混合、候选翻译、长按变形活用候选。
- 支持手动分词符、模糊语种（视语言插件而定）、输出变形后的动词（变形规则视语言插件而定）。
- 用户可以随时切回系统输入法；内置输入法不能阻塞阅读/写作主流程。
- 输入法是规划能力；未实现前不得写成已支持。

### 10. 测试与验收

- 提交前至少运行 `dart tool/verify.dart`；文档改动运行 `dart tool/check_docs.dart`；需要安装包时跑 debug build。
- 单元/widget 测试不得联网；Agent 测试只用 fake provider；不得使用真实 API Key（R-DEV-02、R-AGENT-17）。
- Bug 修复尽量补回归测试；无法自动化的设备/视觉问题，在 PR 记录手工验证步骤和结果。
- OCR/MDict/MeCab/Agent 改动按 [`开发环境与构建`](../05-参考/开发环境与构建.md) 跑设备测试；至少覆盖 x86_64 模拟器与 arm64 真机。
- UI 改动检查 200% 字体、窄屏、语义与触控；当前仅浅色主题。
- Agent 改动必须断言请求体不含图片、base64、路径、文件名、Key；citation/严格/宽松/历史隐私测试按 [`助手契约`](../02-设计/助手/助手契约.md) 执行。
- 性能/测试基线只引用 [`项目数据`](项目数据.md)，不在代码或文档中复制数值。
- 发布前：debug build 后再手动安装；release 先 `--config-only`；用 `aapt dump badging` 校验包名、版本、应用名。
- 真机/真实 provider/secure storage/arm64 Agent 未验收前，不得写“已验证”。

### 11. 文档与知识沉淀

- [`文档索引`](../README.md) 是唯一入口；新增/移动文档必须登记，并运行 `dart tool/check_docs.dart`（R-DOC-12）。
- 每份当前文档必须有状态横幅；文件名中文、无空格、无全角标点（R-DOC-13/14）。
- 权威层级：规则 > 数据 > 设计 token > Agent 契约/schema > ADR > 进度 > 历史；冲突时修正低权威摘要（R-DOC-07）。
- 不在其他文档复制规则正文、当前数值、固定文案、Agent 字段；只引用规则 ID/链接（R-DOC-01/02/03/04）。
- `项目数据.md` 只维护当前测试/设备/性能/构建/环境/预算/固定文案；修改其中原有 Agent 数据前必须取得用户同意（R-DOC-11）。
- 历史文档保留当时值，不用当前值回填；`docs/04-历史/原始需求` 按用户约定保持只读（R-DOC-05）。
- 新误区/踩坑写到 [`误区与踩坑`](误区与踩坑.md) 的 `T-###`；新架构决策写 ADR；当前进度写 `03-进度/`（R-DOC-09）。
- 版本标签统一按 [`版本命名`](../07-维护/版本命名.md)；不要混用阶段、工作包、反馈波次、优先级。
- 一次性脚本用完删除；可复用脚本放 `tool/` 并写清用法，不留下临时文件。
- AI 生成的文档必须核对事实、链接、数值、状态；不得把推测写成当前能力。

## 五、沟通与复盘

### 1. Issue 与看板

- 所有待开发功能、Bug、技术债必须录入 GitHub Issues，不靠口头需求。
- Issue 至少写：背景/目标、范围/非目标、验收标准、涉及模块、隐私/数据影响、测试计划。
- 建议标签：`area/*`（app/reader/write/community/me/ocr/mecab/mdict/agent/worker/supabase/docs）、`type/*`、`priority/高|中|低`、`status/blocked|needs-review|needs-device`、`privacy`、`breaking-change`。
- 看板状态：Todo → In Progress → Review → Done；状态变化及时更新。
- PR 关联 Issue；Issue 在验证通过后才关闭。

### 2. 决策与记录

- 架构、数据模型、隐私边界、依赖引入等决策写 ADR，放在 `docs/02-设计/架构决策/`；一个 ADR 只记录一个决策。
- 已接受的 ADR 不直接改写；需要变更时新增 ADR 并在旧 ADR 标注“由新 ADR 取代”。
- 跨模块契约变更同步更新 [`助手契约`](../02-设计/助手/助手契约.md)、schema、接口文档，并通知相关 owner。
- 不在聊天里做唯一决策记录；结论回写到 Issue/ADR。
- 有分歧时升级到用户/产品负责人，不合并有争议的改动。

### 3. 同步与阻塞

- 异步优先；Issue/PR 评论是主要决策记录。
- 阻塞超过 2 小时，立即求助，并附上“已尝试什么、报错是什么、期望是什么”；不要独自埋头。
- Review 首次反馈目标 1 个工作日内；无法及时 review 时主动转交。
- 可选每周 15 分钟同步：进展、阻塞、下周计划；不做形式化汇报。
- 每次发布后简短复盘：出了什么问题、哪些检查可以自动化、需要更新哪份文档/清单。

### 4. 安全事件

- Key 泄露：立即吊销/轮换；从工作区移除；通知团队；只有在明确批准后才重写历史；补 grep/测试防线。
- 用户数据/图片泄露：停止发布，评估范围，按隐私政策通知，补回归测试。
- 不删除证据；保留脱敏后的日志。
- 不使用真实用户数据做测试；用合成数据/fake provider。
