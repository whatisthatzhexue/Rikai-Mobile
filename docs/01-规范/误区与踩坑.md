## 1. 架构与 OCR（T-001–T-005）

### T-001 把 PaddleOCR4Android 的 Paddle-Lite/OpenCV/NDK r21 模块塞进 Flutter

**误区**：把 PaddleOCR4Android 的 Paddle-Lite + OpenCV + NDK r21 模块直接塞进
Flutter。

**正确做法**：MVP 统一 ONNX Runtime；横向用 PP-OCRv5 ONNX，纵向用 manga-ocr
ONNX。PaddleOCR4Android 只保留在 `third_party/paddleocr4android/` 作为可选后端
说明；二期若接入，做成独立 AAR + `OcrBackend`，不要改主插件依赖。

### T-002 把 `.nb` 模型给 ONNX Runtime，或把 ONNX 给 Paddle-Lite

**误区**：模型格式混用，或改扩展名伪装。

**正确做法**：模型格式由 `assets/models/manifest.json` 固定；`.nb` 只属于
Paddle-Lite，ONNX 只属于 ORT；不要混用，也不要改扩展名伪装。

### T-003 用 `flutter_html` 渲染 MDict 词条

**误区**：用 `flutter_html` 代替 WebView 渲染词典 HTML。

**正确做法**：用 `flutter_inappwebview` 离线 WebView；词典 CSS/表格/MDD 图片需要
完整浏览器布局。若 WebView 有问题，修 WebView 配置（本地文件、CSS 注入、资源
重写），不要退回 `flutter_html`。

### T-004 各 OCR 引擎 `close()` 时关闭共享 `OrtEnvironment`

**误区**：每个 OCR 引擎关闭时把应用级 ONNX Runtime 环境一起关闭。

**正确做法**：`OrtEnvironment` 做应用级单例；引擎只关闭自己的 `OrtSession`。
upstream `PaddleOcrEngine.close()` 有关闭共享环境的问题，抽取时必须修掉；R8
keep `ai.onnxruntime.**`。

### T-005 在 x86_64 模拟器上评估 OCR 性能

**误区**：把模拟器耗时当作真机性能或验收结果。

**正确做法**：模拟器只做功能冒烟；性能、内存、竖排质量用 arm64 真机，记录到
对应阶段状态文档；不要把模拟器数据当作当前验收结果。

## 2. UniDic / MeCab（T-006–T-010）

### T-006 因为 `mecab_for_dart` 要求 `<dicdir>/mecabrc` 就往用户 UniDic 目录写文件

**误区**：在用户 UniDic 目录创建 `mecabrc`。

**正确做法**：已 patch `packages/mecab_for_dart/src/dart_ffi.cpp`：只有该文件存在时
才传 `-r <dicdir>/mecabrc`。应用在**私有目录**创建 `mecabrc`，用
`Mecab.create(dictDir: path, options: '-r "<私有rc路径>"')` 传入。该方式已在
Android x86_64 模拟器 + 真实大型 UniDic 上验证成功；不需要改 C++ 的
`rcPath` 参数，**不要**写用户目录。

### T-007 把 UniDic 复制到 app 存储“更稳”

**误区**：默认把大型 UniDic 复制进应用存储。

**正确做法**：用户明确选择原地路径；不要默认复制大型 UniDic。权限不足时引导
All Files Access，或让用户放到
`/sdcard/Android/data/com.rikai.mobile/files/`。外部存储 mmap 失败时记录具体
错误并**询问用户**，不要静默改成复制方案。

### T-008 硬编码 29 字段并假设所有 UniDic 版本一致，或用 `split(',')` 解析 feature

**误区**：硬编码 29 字段并假设所有 UniDic 版本一致；用朴素 `split(',')` 解析
feature 行。

**正确做法**：解析前校验字段数；字段数异常时降级为“可点击、无注音”，记录日志，
不崩溃。当前 2025.12 版本为 29 字段。

**重要**：UniDic 的 feature 行是带双引号的 CSV，字段内可含逗号，例如
`"動詞%F2@1,形容詞%F4@-2"`。直接用 `TokenNode.features`（朴素 split）会把
助動詞/助詞解析成 30–31 字段。必须用
`lib/services/mecab/mecab_output_parser.dart` 的引号感知解析器。

索引：0-3 pos1-4；4 cType；5 cForm；6 lForm/語彙素読み；7 lemma；8 orth；
9 pron；10 orthBase；11 pronBase；12 goshu；20 kana；21 kanaBase；24-26 accent；
27 lid；28 lemma_id。

### T-009 注音直接用 `lemma` 或 `pron`

**误区**：把词形或发音字段直接当注音。

**正确做法**：优先 `kana`(20)，回退 `pron`(9) → `lForm`(6) → `surface`；
片假名转平假名。未知词可从 MDict 词条提取读音作为 批次 C 兜底。

### T-010 在根包用 `dart run` 跑 MeCab/MDict 主机脚本

**误区**：在项目根包直接运行依赖 native assets 的主机脚本。

**正确做法**：根包依赖 `mecab_for_dart`，Windows 上会触发 native-assets hook 并
失败。主机脚本放到隔离 Dart 包（只依赖 `dict_reader`），例如把
`tool/spike_mdict.dart` 复制到临时包再跑；Android 上的 MeCab 验证在 app 内做。

## 3. MDict（T-011–T-014）

### T-011 把 `locateAll` 返回的内容直接当最终 HTML

**误区**：忽略 `@@@LINK=` 重定向，把链接文本直接渲染。

**正确做法**：读取后先匹配 `^@@@LINK=(.+)$`，最多解析 3 层并防环，再清洗/渲染。
真实测试词典的 `東京`、`食べる` 都是重定向；已用 `tool/spike_mdict.dart` 验证。

参考实现：

```dart
Future<({String key, String html})> resolve(
  DictReader reader,
  RecordOffsetInfo hit, [
  int depth = 0,
]) async {
  final html = await reader.readOneMdx(hit);
  final m = RegExp(r'^@@@LINK=(.+)$').firstMatch(html.trim());
  if (m != null && depth < 3) {
    final next = await reader.locate(m.group(1)!);
    if (next != null) return resolve(reader, next, depth + 1);
  }
  return (key: hit.keyText, html: html);
}
```

### T-012 启动时打开所有词典并常驻

**误区**：在主 isolate 初始化全部词典，拖慢启动并占用大量内存。

**正确做法**：懒初始化 + 长生命周期 worker isolate；只打开启用的词典。大词典的
初始化耗时/内存按实际设备测量；需要时用 `exportCache/importCache` 或 SQLite
key 索引，不要在主 isolate 初始化。

### T-013 使用已废弃的 `init()`

**误区**：按旧版 `dict_reader` API 调用 `init()`。

**正确做法**：用 `dict_reader` 1.6.1 的 `initDict()`。不支持 LZO / record block
加密 / v3 时，在导入预检阶段明确报错，不要等运行时崩溃。

### T-014 WebView 直接加载词典 HTML

**误区**：把未经清洗的 MDict HTML 直接交给 WebView，或允许网络/JS。

**正确做法**：`package:html` 清洗 `<script>/<iframe>/<object>/<embed>/<form>`、
`on*` 事件、`javascript:` URL；注入外部 CSS；MDD 资源按需提取到缓存并重写
`src` 为本地 `file://`。WebView 设置：`javaScriptEnabled: false`、
`blockNetworkLoads: true`、仅本地文件；`shouldOverrideUrlLoading` 拦截
`entry://` 与外部 URL。

## 4. Android / 权限 / 构建（T-015–T-020）

### T-015 认为 `permission_handler` 可以处理“所有文件访问”

**误区**：继续使用 `permission_handler` 申请所有文件访问。

**正确做法**：当前 `permission_handler_android 14.1.0` 的 Kotlin DSL 与
Gradle/Kotlin 组合编译失败，已移除。改用原生 MethodChannel：

- `Build.VERSION.SDK_INT >= 30`：`Environment.isExternalStorageManager()` 检查；
  未授权时跳转 `Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION` +
  `Uri.parse("package:$packageName")`。
- Android 10 及以下：申请 `READ_EXTERNAL_STORAGE`。
- Manifest 已声明 `MANAGE_EXTERNAL_STORAGE`、`READ_EXTERNAL_STORAGE`
  （maxSdk 32）、`requestLegacyExternalStorage`。
- 已实现于 `android/app/src/main/kotlin/com/rikai/mobile/MainActivity.kt` 和
  `lib/services/storage/permission_service.dart`（channel
  `rikai/storage_permission`），设备端测试已验证。

### T-016 路径有中文就加 `subst` / `overridePathCheck` / `kotlin.incremental=false`

**误区**：为旧路径问题恢复各种 Gradle 规避配置。

**正确做法**：项目已在 `C:\Projects\Rikai-Mobile`（ASCII），这些配置已从
`android/gradle.properties` 删除，不要恢复；直接构建即可。

### T-017 Gradle `metadata.bin` 错误只能删整个缓存/重装

**误区**：删除整个 Gradle 缓存或重装环境。

**正确做法**：

```powershell
cd C:\Projects\Rikai-Mobile\android
.\gradlew --stop
$c = "$env:USERPROFILE\.gradle\caches\8.14"
Move-Item "$c\kotlin-dsl" "$c\kotlin-dsl.bak"
Move-Item "$c\groovy-dsl" "$c\groovy-dsl.bak"
Move-Item "$c\transforms" "$c\transforms.bak"
Move-Item "$c\generated-gradle-jars" "$c\generated-gradle-jars.bak"
Move-Item "$c\dependencies-accessors" "$c\dependencies-accessors.bak"
```

保留 `modules-2`；再用 `.\gradlew :app:assembleDebug --no-daemon` 诊断。

### T-018 NDK 用 Flutter 默认或随意降级

**误区**：修改 NDK 版本以绕过构建问题。

**正确做法**：`android/app/build.gradle.kts` 固定 NDK/compileSdk/targetSdk/minSdk，
具体值以该构建文件为准（`jni` 插件要求）；不要降 NDK。

### T-019 release 构建随时可跑、很快

**误区**：把 release 当普通构建，或在耗时任务中直接中断。

**正确做法**：release 需要 arm64 + R8，耗时数分钟；用户曾中断一次，需要时先确认。
命令：`flutter build apk --release --target-platform android-arm64
--split-per-abi`。Debug APK ~260MB 不代表 release 大小。

### T-020 未要求就 commit/push/reset

**误区**：擅自提交、推送、重置或覆盖用户未提交改动。

**正确做法**：先 `git status`；只改代码/文档；不 commit/push；不覆盖用户未提交
改动；结束时报告未提交文件。

## 5. 许可 / 仓库 / 范围（T-021–T-025）

### T-021 模型/词典可以随仓库提交

**误区**：把 `.onnx`、`.mdx`、`.mdd`、UniDic 或字体提交进仓库。

**正确做法**：`.gitignore` 已覆盖模型/词典/UniDic；只提交

`git ls-files | grep -E '\.(onnx|nb|mdx|mdd)$'` 验证；模型下载到

**误区**：把 `l0wgear/manga-ocr-2025-onnx` 权重随包分发或提交。

**正确做法**：`l0wgear/manga-ocr-2025-onnx` 模型卡未声明许可；只下载/本地导入，
不随包分发；下载前显示警告；保留 `NOTICE` 说明。`kha-white/manga-ocr-base` 是

### T-023 删除 `unidic/`、`mdicts/`、两个上游 clone 来“清理仓库”

**误区**：把被忽略的开发数据/参考代码当成仓库垃圾删除。

不提交；`overlay-translator/`、`PaddleOCR4Android/` 仅作参考。

### T-024 把 阶段 6 的在线 Agent 当成“给项目加 LLM/云 OCR”，或反过来继续声称纯离线

**误区**：把可选文本 LLM Agent 理解成云 OCR/云翻译，或在未配置时默认联网。

**正确做法**：MVP/核心仍锁定 Android 单端、离线 OCR/分词/词典；不引入 iOS、
ML Kit 或云 OCR/云翻译。阶段 6 是**可选的用户配置文本 LLM Agent**：必须单独
批准，默认不联网，图片不上传，不使用 provider 视觉，不把 API Key 写入仓库/日志；
未实现前文档只能写 planned/design。

### T-025 恢复旧包名/旧 MainActivity

**误区**：恢复 `com.rikai.rikai_mobile` 或旧入口类。

**正确做法**：统一 `com.rikai.mobile`；唯一入口是
`android/app/src/main/kotlin/com/rikai/mobile/MainActivity.kt`；旧
`com/rikai/rikai_mobile/MainActivity.kt` 只是注释，不要恢复类。

## 6. 设备实测与开发流程（阶段 1，2026-10-27）（T-026–T-039）

### T-026 在 Git Bash 里直接传 `/sdcard/...` 给 adb 或 `--dart-define`

**误区**：忽略 MSYS 路径转换，命令收到 `C:/GitBash/sdcard/...`。

**正确做法**：MSYS 会把路径改写成 `C:/GitBash/sdcard/...`。运行前
`export MSYS_NO_PATHCONV=1`，对 `adb push`、`adb shell`、`flutter test` 都适用。

### T-027 `flutter test integration_test/...` 跑完仍保留应用与权限

**误区**：认为集成测试后应用和 `MANAGE_EXTERNAL_STORAGE` 授权仍在。

**正确做法**：该命令测试前安装、测试后卸载应用，`MANAGE_EXTERNAL_STORAGE`
appops 随之丢失。用同一 shell 的后台循环在应用出现后反复执行
`adb shell appops set com.rikai.mobile MANAGE_EXTERNAL_STORAGE allow`；集成测试
会轮询最多 120 秒等待 UniDic 可读。命令按设备集成测试流程执行。

### T-028 忽略 Riverpod 3 的默认 retry

**误区**：让失败 provider 无限重试，导致 spinner 永不结束。

**正确做法**：Riverpod 3 默认指数退避重试失败 provider；无效 UniDic 会反复
初始化，spinner 永不结束。`mecabServiceProvider` 已设
`retry: (_, __) => null`；其它加载大文件/原生资源的 provider 也应显式关闭。

### T-029 外部存储 mmap 不可用

**误区**：预先假设 `/sdcard/Download` 无法 mmap，改用复制方案。

**正确做法**：已在 x86_64 API 36 模拟器验证 `/sdcard/Download` mmap 可用；
`MecabService.open` ~246ms。arm64 真机仍需复测。

### T-030 widget 测试里用 `pumpAndSettle` 等待真实文件 I/O 或权限通道

**误区**：在真实异步 I/O / MethodChannel 场景用 `pumpAndSettle`。

**正确做法**：mock `rikai/storage_permission`；真实文件 I/O 用 `tester.runAsync`
让出事件循环，否则无限 spinner 会让 `pumpAndSettle` 超时。

### T-031 把 HarmonyOS Sans 字体提交到仓库，或页面里硬编码颜色/字号

**误区**：提交字体文件；页面散落 `Color(0x...)` / `fontSize: 数字`。

**正确做法**：`assets/fonts/*.ttf` 已被 `.gitignore` 忽略；用户按
`assets/fonts/README.md` 自行下载。UI 必须使用
`lib/core/theme/app_tokens.dart` 与 `AppTheme.light()`，禁止散落
`Color(0x...)`/`fontSize: 数字`（阅读区用户字号除外）。

### T-032 把 MDD key 直接当作 HTML 的 `src` 交给 `DictReader.locate`

**误区**：忽略 MDD key 的前导反斜杠/斜杠差异，导致图片空白。

**正确做法**：HTML 常写 `JC_Z24Z/A471.png`，MDD 实际 key 是
`\JC_Z24Z\A471.png`。必须用 `lib/services/mdict/mdd_key.dart` 生成前导反斜杠、
斜杠/反斜杠、`file://` 与 percent-encoded 变体。

### T-033 WebView 直接加载原始 MDict HTML，或用字符串 loadData 而没有 file base URL

**误区**：用字符串 `loadData` 且没有 file base URL，导致 CSS/图片不加载。

**正确做法**：`EntryRenderer` 清洗后，用 `InAppWebViewInitialData` +
`baseUrl: WebUri('file://.../<dictId>/')`；`allowFileAccess: true`、
`javaScriptEnabled: false`、`blockNetworkLoads: true`。MDD 图片先写入缓存目录
并重写为绝对 `file://` URL，否则 Android WebView 图片空白。

### T-034 只移除 `</style>` 就算清理了词典 CSS

**误区**：只处理结束标签，字典 CSS 仍可逃逸或注入脚本。

**正确做法**：CSS 注入前移除 `</style>`、`<script>` 等标签序列
（`EntryRenderer._stripStyleClose`），防止字典 CSS 逃逸出 `<style>`。同时清洗
`on*`、`srcdoc`、`srcset`、`javascript:`/`vbscript:`/`data:text/html`，并阻断
网络图片。

### T-035 用 dictionary 原始文件名/中文路径做设备集成测试，或在搜索 loading 时用 `pumpAndSettle`

**误区**：设备测试依赖中文路径；持续动画页面用 `pumpAndSettle` 等待。

**正确做法**：把测试词典以 ASCII 名 push 为
`/sdcard/Download/rikai-mdict/{dict.mdx,dict.mdd,dict.css}`（MDX/MDD 必须同
basename 才会自动发现）；`flutter test` 会重装应用，需后台循环重授 All Files
Access；搜索/词条页有持续动画时用定时 `tester.pump` 轮询，不要
`pumpAndSettle`。

### T-036 用 `file_picker.pickFiles` 选择用户的 .mdx，然后把返回路径存起来

**误区**：忽略文件选择器会把文件复制到应用 cache，导致同目录 MDD 丢失。

**正确做法**：该版本的 Android 文件选择会把文件**复制到应用 cache**，同目录 MDD
不会一起复制，违反原地读取。用 `FilePicker.getDirectoryPath` 让用户选文件夹，
再在 Dart 中列出该目录的 `.mdx` 并确认；UniDic 同理只选目录。

### T-037 每次打开词条都重新初始化词典/重新渲染 HTML

**误区**：不预热 worker、不做渲染缓存，逐次重复初始化。

**正确做法**：`BootstrapApp` 在启动页对 `enabledDictionariesProvider` 调用
`MdictService.warmUp`（worker 常驻）；`EntryRenderCache` 以 dictionaryId +
词条 HTML 哈希做内存 LRU；revalidate/remove 时失效。

### T-038 点击一个搜索结果却把该词的所有词典/词条都显示出来

**误区**：单条结果点击后展示该词的全部词典分组。

**正确做法**：单条点击只传 `DictionaryLookupGroup(entries: [entry])`；同词典结果
≥2 条时显示“查看全部（N 条）”，点击只传该词典的完整 group。`entry://` 链接取
第一个结果。

### T-039 改主页顶栏时直接改全局 `AppBarTheme`，导致设置/词条页也变深蓝

**误区**：早期只给主页单独设置深蓝顶栏，后来改成全局时按页面单独设白底。

**正确做法**（已被 2026-10-28 二次要求覆盖）：现在**所有页面**统一深蓝 AppBar +
白字；不要再按页面单独设白底。详见 `T-041`。

## 7. UI / 启动修正（2026-10-28）（T-040–T-051）

### T-040 设备集成测试后直接安装 `app-debug.apk` 手动验收

**误区**：集成测试覆盖了 debug APK 后直接安装，应用停在系统启动图，被误判为
业务代码死锁。

**表现**：应用停在系统启动图，Dart isolate 空闲、无 Flutter 首帧；VM service 里
出现 `ext.flutter.integrationTest`，缺少 `ext.flutter.debugDumpApp` 等框架扩展。

**正确做法**：`flutter test integration_test/...` 会用测试入口覆盖
`build/app/outputs/flutter-apk/app-debug.apk`；手动安装前必须重新
`flutter build apk --debug`。这是启动图卡死的首要排查项，不要误判为业务代码
死锁。

### T-041 只在主页设置深蓝顶栏，其他页面保留白色 AppBar

**误区**：页面局部设置顶栏颜色，导致设置/词条页仍为白底或深色字。

**正确做法**：`AppBarTheme` 全局深蓝 `header` + 白字/白图标、
`systemOverlayStyle: light`、无底部分割线；页面不要局部覆盖颜色。词条页 TabBar
位于深蓝顶栏内，使用白色 label/indicator，不要用品牌蓝。

### T-042 设置页用 Card 包住输入框和操作按钮，或把长提示塞进 `helperText`

**误区**：设置页组件套组件；长提示被单行截断。

**正确做法**：白底扁平分区；TextField/按钮直接放在页面上；长提示不要塞进
`InputDecoration.helperText`，改为输入框外独立 14sp Text，允许换行；用户不可变
信息（外部私有目录）用 16sp 纯文本；长权限说明用自定义 Row/Column，而非可能
截断的 ListTile subtitle。

### T-043 主页功能按钮沿用首版的 40sp/左对齐/亮品牌蓝

**误区**：按钮字号、颜色、对齐与已确认设计不一致。

**正确做法**：按钮背景与顶栏相同 `AppColors.header`；图标+文字整体居中；文字
32sp（40sp 的 80%）；抽屉 `Drawer.shape` 使用直角。

### T-044 帮助/著作权继续用 Card/ListTile 小字

**误区**：帮助/著作权页继续使用卡片和 12sp 小字。

**正确做法**：白底纯文本；正文 16sp、栏目标题 18sp、每栏之间 Divider；不嵌套
卡片。

### T-045 查词结果沿用 12sp 的 titleSmall/labelSmall，且用 ListTile 承载 24sp 标题

**误区**：查词结果的词典名/条目数过小；大字号标题被 ListTile 裁切。

**正确做法**：词典名/条目数 16sp 同色（与“查看全部”一致）；词条标题 24sp；
摘要 14sp；用自定义 Card+InkWell+Column，避免大字号被 ListTile 裁切。

### T-046 切换字体时只改 `ThemeData(fontFamily:)`，组件主题仍写死 HarmonyOS

**误区**：只改全局 fontFamily，显式 TextStyle 仍使用 HarmonyOS。

**正确做法**：`AppTheme.light(fontFamily:)` 必须把 family 写入 AppBar、按钮、
对话框、SnackBar、弹层、输入框、ListTile、TabBar 等所有显式 TextStyle；系统字体
时传 null。`ThemeData` 没有 `fontFamily` getter，测试检查
`textTheme.*.fontFamily`。

### T-047 手动编辑 flutter_launcher_icons 生成的 mipmap，或把图标/字体混在一起提交

**误区**：手改生成物；图标源和字体一起入库。

**正确做法**：修改 `assets/Rikai_Icon.jpg` 后运行
`dart run flutter_launcher_icons`；图标源提交，字体不入库；原生启动图使用
`drawable-nodpi/launch_icon.png`，Android 12+ 系统启动图使用 adaptive icon
（圆形遮罩属正常）。

### T-048 页面跳转沿用 Material 默认的淡入/缩放转场

**误区**：新旧页面交叉淡化，深蓝顶栏在过渡瞬间发白。

**表现**：旧页与新页交叉淡化，深蓝顶栏在过渡瞬间发白，出现白色瑕疵。

**正确做法**：`AppTheme.light()` 的 `pageTransitionsTheme` 在全部平台使用
`SlideOverPageTransitionsBuilder`：新页面从右侧滑入覆盖旧页面，旧页面静止、
无淡入淡出/缩放。不要给单个页面自定义转场；`Navigator.push` 的
`MaterialPageRoute` 与 go_router 都会继承全局主题。

### T-049 阅读器工具区没有浅色收边，或为了收边把工具区改成灰色底带

**误区**：缺少自然分隔，或把白色工具区改成灰色底带。

**表现**：输入框/分词/复制区域与长文分词列表之间缺少自然分隔，或出现用户不
想要的灰色底带；用户明确要求**保留白色工具区**，只保留细边。

**正确做法**：阅读面、结果列表与工具区均为 `AppColors.surface` 白色；工具区
底边仅 1px `AppColors.divider` 细线（`reader-controls-surface` 的
`Border.bottom`）；`TextField` 设 `filled: false`，不额外铺色块。不要为了分隔感
把工具区改成 `background`。

### T-050 阅读器功能词、标点和振假名使用 `textSecondary` 灰色

**误区**：阅读器分词结果整体发灰，层级不清。

**正确做法**：内容词蓝50底 + 蓝700；功能词/标点透明底 + `textPrimary` 近黑；
振假名品牌蓝 `primary`。阅读器内不使用灰色文字，靠蓝色/黑色/字重建立层级；
对应 TokenChip token 在 `lib/core/theme/app_tokens.dart`。

### T-051 查词弹层保留右上角关闭叉；词形与读音相同仍显示蓝字读音

**误区**：弹层多一个关闭叉；`ありがとう（ありがとう）` 这类重复读音仍显示蓝字。

**正确做法**：阅读页查词弹层可下滑/上滑/点击遮罩关闭，移除关闭 IconButton；
仅在 `token.hasDistinctReading` 为 true 时显示蓝色读音行，重复读音只保留黑色
词形。

## 8. OCR 设备经验（阶段 3，2026-10-28）（T-052–T-058）

### T-052 用 `adb push` 往 `/sdcard/Android/data/<pkg>/files/models` 塞模型后直接让 app 读取

**误区**：把模型 push 到 app 专属外部目录，忽略目录属主/权限。

**表现**：`FileSystemException: Exists failed ... Permission denied (errno 13)`，
因为目录是 shell 所有，FUSE 下 app 不能遍历。

**正确做法**：先启动 app/模型页让 app 自己创建目录，再 push 文件到该 app-owned
目录；或用应用内下载/本地导入。集成测试使用
`/sdcard/Download/rikai-models` + All Files Access，避免该问题。

### T-053 在 Git Bash 里给 `flutter build --dart-define=...=/sdcard/...` 传 Android 路径

**误区**：路径被 MSYS 转换，Dart 端收到 `C:/GitBash/sdcard/...`。

**表现**：Dart 端看到 `C:/GitBash/sdcard/...`，模型页报
`Creation failed, path = 'C:'`。

**正确做法**：`export MSYS_NO_PATHCONV=1` 后再 build/test；对 adb push、
`flutter test --dart-define` 同样适用。

### T-054 按旧版 file_picker API 写 `FilePicker.platform.pickFiles()` 并读 `result.files`

**误区**：使用 v13 已移除的静态实例 API。

**正确做法**：v13 是静态 API：`FilePicker.pickFiles()` 直接返回
`List<PlatformFile>`（取消为空列表）；目录选择用
`FilePicker.getDirectoryPath()`。

### T-055 解析 PP-OCRv5 的 `keys.yml` 时用 `trim()`/`rstrip()`

**误区**：解析时删掉字典首个 U+3000 全角空格。

**表现**：字符表变空或 CTC 首字符丢失；该字典第一个 key 是 **U+3000** 全角
空格，Kotlin 的 `trim()`/Python 的 `rstrip()` 会将其删掉。

**正确做法**：按行处理时只去掉 `\r`/`\n`，YAML 标量只去掉 ASCII 空格；
`CtcDictionary.kt` 已按此实现，输出 class 数按模型字典实际长度校验。

### T-056 每个 OCR 引擎 close 时关闭 `OrtEnvironment`，或把竖排请求静默当横排处理

**误区**：关闭共享 ORT 环境；手动竖向缺模型时静默改走横向。

**正确做法**：`OcrRuntime.environment` 应用级单例，不随引擎关闭；阶段 4 的
`vertical` 使用独立的 MangaOCR 引擎，手动竖向缺模型时必须返回 `MODEL_MISSING`，
不得静默伪装成横向；只有 `auto` 允许在 MangaOCR 缺失时回退 Paddle 横向。

### T-057 以为 image_picker 需要 Android CAMERA 权限

**误区**：额外申请 CAMERA 权限，反而导致系统相机 Intent 失败。

**正确做法**：它通过系统相机 Intent 取图，Manifest 只需已有
`<uses-feature camera required=false>`；不要额外申请 CAMERA，否则反而会因为未
授权导致相机 Intent 失败。

### T-058 把 PaddleOCR 识别输入按 RGB 顺序送入模型

**误区**：通道顺序和归一化与训练不一致，导致 OCR 全错/乱码。

**正确做法**：PaddleOCR 训练使用 OpenCV BGR；Bitmap 是 RGBA，必须在
`bitmapToNchw` 中按 B/G/R 写三个通道，并按 0.485/0.456/0.406、
0.229/0.224/0.225 归一化检测输入；识别输入用 0.5/0.5。

## 9. 采集 / 导入 / 语料（阶段 3.5，2026-10-29）（T-059–T-074）

### T-059 继续用 `image_picker` 的系统相机 Intent 冒充实时拍照页

**误区**：没有实时预览/连拍，且多余申请 CAMERA 权限。

**正确做法**：实时预览必须引入 `camera` 插件并声明 CAMERA 权限；预览用
`FittedBox` + 交换 `previewSize` 的宽高 + `BoxFit.cover`。应用进入后台或打开
照片集/阅读页时 dispose 相机，返回时重建；不要用 `permission_handler`。

### T-060 把照片集的删除/保存按钮放在照片区域内部，或把保存做成白底

**误区**：按钮随照片区移动；白底按钮在照片背景下对比不足。

**正确做法**：用户要求它们固定在**整个画面**左下/右下角；照片区只放照片。不再
在底部额外预留 64dp；识别方向、旋转、模型设置、页码导航贴近页面底部，
`CapturePageNavigation` 固定 52dp 高、底边距 12，使页码箭头中心与 52dp
删除/保存按钮中心同高。两者统一使用 `CaptureRoundButton`（52dp、24dp 图标），
删除为错误色、保存为深蓝 `header` + 白图标；白底按钮在照片背景下对比不足。
均二次确认；保存写入 `HistoryStore`（照片副本 + OCR 文本 + blocks + 模式/时间）。

### T-061 在照片集正文再放一个“多选”或“全选”，或再加一行保存文字按钮

**误区**：标题栏与正文重复入口，操作语义混乱。

**正确做法**：照片集标题栏只保留一个「多选」；多选页标题改为「选择照片」，正文
只显示已选数量，全选放标题栏；删除/保存沿用同一 `CaptureRoundButton` 图标，
不再放“保存到语料库（后续支持）”等重复文字。

### T-062 照片集保留“分析句子”按钮，把分词错误塞进结果区，或把复制放标题栏

**误区**：多一步分析操作；错误横幅推挤 OCR 结果；复制入口位置错误。

**正确做法**：用户要求删除分析按钮；已配置 UniDic 时 OCR 完成后自动分词，直接
使用 `ReaderBlock`/`buildReaderLines` 按文本阅读页渲染，点词打开查词弹层。未
配置时显示 OCR 原文；分词失败用**红色横幅叠在照片顶部、标题栏下方**，带白字
“重试”，不能占用/推挤 OCR 结果区。复制按钮改为照片显示区右下角的深蓝
`header` 长条（白字白图标，文案「复制文本」）；标题栏只留字号/注音菜单和
“多选”。字号/注音使用与阅读页同一个 `ReaderOptionsMenu`（16/20/24/28 + 显示
注音）。

### T-063 照片区高度写死；拖拽指示条是白线外套灰色胶囊；拖拽有 slop 不跟手

**误区**：照片区不可调；指示条样式厚重；拖拽慢半拍。

**正确做法**：照片区下边缘提供 40dp 拖拽热区，指示条必须是**纯白单色**
44×4dp（不要深色胶囊/描边）；向下拖动扩大照片区（默认 250、最小 120，给结果/
操作区留空间）。必须用 `Listener` 直接处理 pointer down/move/up，以 drag 起点
的绝对位移计算高度，不能再用 `onVerticalDragUpdate` 的 delta+slop（会慢半拍）。
点击照片进入黑底全屏 `InteractiveViewer`，支持双指缩放与平移，参考系统画册。

### T-064 MDict 批量导入完成弹结果对话框，或扫描时显示 MDD/CSS、Instance of 等英文

**误区**：导入完成弹框打断；扫描行暴露英文尾注/异常。

**正确做法**：扫描行只显示路径、大小和中文状态（可导入/已存在/不支持），不追加
`MDD n · CSS n` 等英文尾注，也不显示原始英文异常；扫描进度不显示文件名。词典
标题若是 `Instance of ...`/`Exception ...` 等 Dart 调试文本，用
`displayDictionaryTitle` 回退文件名。词典管理的资源标签使用“资源/样式/无资源”。
导入结束后直接返回词典管理页；仅在失败/取消时用非阻塞 `RikaiToast` 报告数量，
不要弹“导入结果”对话框。

### T-065 本地导入模型按 manifest 的 det.onnx/rec.onnx 精确文件名匹配

**误区**：上游文件名是 `inference.onnx`/`inference.yml` 时导入失败。

**正确做法**：上游下载常为两个 `inference.onnx` + `inference.yml`；按文件大小、
扩展名和角色映射，命中已安装文件时只补缺失项；先写 `.importing` 校验再替换，
失败清理临时文件。

### T-066 改模型目录只改 UI 文本，或先保存路径再迁移失败

**误区**：迁移失败后设置已指向无效目录，或丢失其它设置。

**正确做法**：先校验新目录读写/空间；默认复制并逐文件校验后再保存设置和删除
旧文件，支持“仅切换”；目录失效时保留设置并提供重新选择，不崩溃、不清空其他
设置。

### T-067 每次从模型设置/多选/其它页面返回照片集都重新 OCR

**误区**：页面重建重置模式；返回时无条件重跑 OCR。

**正确做法**：OCR 缓存键是“照片 + 模式 + 模型指纹”，模式存在
`CaptureSessionState.mode`（会话级，不得因页面重建重置为自动）。
`OcrService.fingerprint` 在应用会话内保留；照片集先用它查缓存并直接渲染，无需
`ensureReady`。模型设置返回时只有指纹变化才清缓存并 `force` 重新识别；指纹不变
必须 `_refreshCurrent(force:false)`。多选页传入 `initialFingerprint`，进入时先查
缓存，只补识别缺失照片；全部命中时不要显示/闪一下进度。

### T-068 主页功能按钮仍在最上方，使用前须知在下方；或继续把按钮组垂直居中

**误区**：信息顺序不符；按钮组占用剩余空间居中。

**正确做法**：按 Column 顺序排列“使用前须知 → 功能按钮区 → 边界说明”（小屏可
滚动；按钮数量/文案按当前产品定义）。保持深蓝 `header`、32sp、按钮内容居中，
但不再做整组垂直居中。

### T-069 语料页沿用 72dp 缩略图和右侧小删除按钮；点击语料仍跳文本阅读页

**误区**：列表信息不足；点击行为与已确认的语料详情不一致。

**正确做法**：语料列表与详情标题栏右上角都提供 `ReaderOptionsMenu`；分词按
`readerFontSize` 渲染。语料列表用与照片集多选页一致的两列紧凑卡片：完整
contain 照片 + 最多 3 行 OCR + 日期 + 右上错误色圆形删除 + 右下「复制」。点击
进入 `/corpus-detail`（`CorpusDetailPage`）：照片/分词，照片右下「复制文本」，
语料间页码，标题「语料」，左下删除；不重复显示 OCR 原文和日期；无多选/方向/
模型设置/保存。该页只使用本机图片、`HistoryStore`、MeCab/MDict，不得联网。

### T-070 语料详情把 OCR 原文和分词结果都堆在长页面里

**误区**：详情重复显示 OCR 原文，页面冗长。

**正确做法**：详情只显示分词结果（`ReaderBlock`，可点词查词）；未配置 UniDic/
失败时给中文说明/重试。翻页/删除后重新分析当前语料，旧分析用 token 丢弃。

### T-071 加入 MangaOCR 后仍只按 PaddleOCR 文件计算照片集缓存指纹

**误区**：安装/删除可选模型后仍复用旧模式缓存。

**正确做法**：使用 `OcrRuntimePaths` + `fingerprintForPaths`，指纹包含 Paddle、
已安装的 MangaOCR（encoder/decoder/vocab）和 orientation 文件；可选模型缺失时
写入 `manga=off` / `orientation=off`，安装/删除后必须使照片集缓存失效，否则
auto/vertical 会复用旧横向结果。

### T-072 可选 MangaOCR/orientation 加载失败就让整个 OCR 初始化失败

**误区**：可选模型故障阻断横向 OCR。

**正确做法**：Paddle 为必需；MangaOCR/orientation 独立加载，失败只记录
`mangaError`/能力状态。横向 OCR 必须继续可用；只有手动 `vertical` 才返回
`MODEL_MISSING`/`MODEL_INVALID`，`auto` 在缺少 Manga 时回退横向。

### T-073 用框高宽比单独判断竖向，方形字框组成的单列会误判为横排

**误区**：只看单框高宽比，忽略方形字框的纵向堆叠。

**正确做法**：`TextLayoutHeuristic` 额外识别“x 中心接近、y 连续堆叠”的方形框列
（≥3 个、纵向跨度 ≥2.5 倍框高），作为竖向候选；仍由 MangaOCR 处理。不要把它
误当成横排 logo。

### T-074 textline 180° 模型在只有一条文本行时永远不触发

**误区**：投票阈值只按多行设计，单行倒置页漏检。

**正确做法**：两行以上要求 ≥2 个 180° 投票且占比 ≥0.6；只有一条高置信
（≥0.99）180° 行时允许单独触发。旋转 180° 后必须重新跑 DBNet，不能只旋转识别
用的 crop；坐标仍以旋转后的图像为准。

## 10. Agent 设计期（阶段 6）（T-075–T-081）

### T-075 把图片/base64 或图片路径发给 LLM，让模型“顺便看看图”

**误区**：把图片或图片路径作为 provider 输入，或调用视觉能力。

**正确做法**：图片只在本机走 OCR；provider 请求体只能包含文本、分词/词典查词
结果和 schema。捕获请求测试必须断言没有图片字段/base64；严禁调用 provider 的
视觉能力。

### T-076 严格模式没有词典依据时让模型补充一个“看起来合理”的答案

**误区**：严格模式编造词义/读音/翻译，或把宽松补充混入词典事实。

**正确做法**：严格模式的事实性陈述必须有真实词典 citation；没有依据就明确说明
未找到，不得编造词义/读音/翻译。宽松模式的模型补充必须与词典事实分开标注，
不能混在一起。

### T-077 把模型输出里的 `[来源1]` 直接当可信来源打开

**误区**：信任模型自造/越界的 citation ID，导航到任意词条。

**正确做法**：citation ID 由 orchestrator 根据真实词典查词结果发放并校验；伪造/
越界/失效 citation 只按普通文本显示，不能打开任意词典页。

### T-078 API Key 放进 SharedPreferences、URL、日志或崩溃报告

**误区**：Key 出现在持久化配置、请求 URL 或日志中。

**正确做法**：使用 Android Keystore/安全存储；日志/导出/错误信息脱敏；提供清除
Key 和配置的入口；仓库中不得出现真实 Key。

### T-079 每次新会话都重新让 Agent 探查词典

**误区**：重复采样/生成词典熟悉文档，或把档案写进用户目录。

**正确做法**：词典熟悉文档按词典路径/stat、UniDic 版本和 schema/prompt 版本
缓存；用户确认后复用；词典变化/用户重置时失效。不要把熟悉文档写入用户的
UniDic/MDict 目录。

### T-080 允许 Agent 生成并直接执行任意 Dart/JS/Python 伪代码

**误区**：把模型输出当代码执行，或允许任意文件/网络访问。

**正确做法**：转换成受验证的安全 DSL（白名单字段/样式），支持预览、用户确认、
版本/回滚；统一 annotation engine 作用于所有 UniDic token 展示。禁止文件/网络/
反射/任意代码执行。

### T-081 为了 阶段 6 提前调整主页功能按钮/改文案，或把 planned 写成已实现

**误区**：功能未实现先改入口/文案；文档把 planned 写成已支持。

**正确做法**：P6.5 已接入功能按钮并同步更新文档、设计 token 与测试；P6.6 多 OCR
应用了既有 Agent token 并补了测试；P6.7 的新 UI 仍必须先补 token 与测试，不能把
未实现能力写成已支持。

## 11. OCR 收敛（阶段 4.5）（T-082–T-112）

### T-082 每次 `ensureReady` 都重新创建全部可选 session / 全量 SHA-256

**误区**：ready 检查过重，拖慢首次识别并反复校验大文件。

**正确做法**：Paddle 必需；Manga/orientation 懒加载；readiness 先 stat；SHA 只对
下载/导入/迁移等写入路径执行，并按 path+size+mtime 缓存。不要把 `mangaReady`
当成 session loaded。

### T-083 每次 auto 都跑 doc orientation，或在正方形/正常竖排页上旋转整图

**误区**：无条件跑方向模型/旋转，增加耗时并可能误转。

**正确做法**：只在图像长宽比与 DBNet 布局矛盾时运行；高置信 90/270 才旋转；
旋转后必须重新 DBNet；textline 180° 只在 auto 横向。

### T-084 auto 同时跑两个引擎/输出 mixed 结果，或让低置信度 Manga 直接返回

**误区**：按区域混合输出；低质量 Manga 结果不回退。

**正确做法**：auto 只返回 `paddle_v5` 或 `manga_ocr` 之一；Manga 平均置信度低于
0.75 时回退 Paddle。模式切换必须强制重新识别，不能复用旧模式缓存。

### T-085 MangaOCR 固定 gap/padding，且不过滤低置信度噪声

**误区**：不随框尺寸缩放布局；为提高召回保留乱码。

**正确做法**：gap/padding 按检测框中位尺寸缩放；清除控制/替换字符；低于保守
阈值的 bubble 丢弃。不要为了提高召回保留明显乱码。

### T-086 照片旋转直接改设备原图，或旋转后仍用旧 OCR 缓存

**误区**：破坏原图；旋转后复用旧结果。

**正确做法**：只旋转 `CaptureStorage` 私有会话副本 90°；清该照片 OCR 缓存、
evict `FileImage`、重新识别；设备原图不变。

### T-087 把 MDX/MDD 的 `Encrypted: 2` 当成加密词典直接拒绝

**误区**：把 record-block 布局误判为不可读加密。

**正确做法**：`Encrypted: 2` 是 dict_reader 可读的 record-block 布局；只有
`Encrypted: 1` 和 v3 仍拒绝。MDD 缺失时 worker 可发现同目录同名 `.mdd`，
`../`/`./` 资源前缀由 `mddKeyCandidates` 归一化。

### T-088 外部路径直接校验/扫描，失败后才让用户找设置

**误区**：未确认 All Files Access 就访问 `/sdcard`、`/storage`。

**正确做法**：选择或使用 `/sdcard`、`/storage` 等沙盒外路径前调用
`ensurePathAccess`；未授权时弹窗并跳到系统“所有文件访问”页面。应用专属外部
目录不需要该权限。

### T-089 退出模型下载页就取消下载；或取消时删除 `.part`

**误区**：离开页面即中断；取消后无法续传。

**正确做法**：默认后台继续，退出弹窗提供“同时停止下载”（默认不勾选）；`.part`
保留并用 HTTP Range 续传；设置页“清除模型缓存”只删临时文件。

### T-090 EntryPage 退出时让 platform WebView 参与整个 pop 动画

**误区**：WebView 参与长转场，出现闪帧/卡顿。

**正确做法**：监听 route reverse，把 WebView 换成页面底色；转场 220ms/180ms。
WebView 退出闪帧和大部分卡顿来自 platform view 参与长动画。

### T-091 认为 MDict 音频只需要保留 `sound://` 链接

**误区**：WebView 无法播放 MDD 内的音频资源。

**正确做法**：`EntryRenderer` 解析 `sound://key` 到 MDD 资源，写成缓存文件并插入
本地 `<audio controls>`；`mddKeyCandidates` 同时去掉 `sound://` 前缀。WebView 需
`allowFileAccess` 和 `allowFileAccessFromFileURLs: true`，JS 仍保持关闭。
`日本語文型辞典 三语音频版` 的 `00048.aac` 已在 x86_64 模拟器通过
`mdict_audio_android_test.dart` 验证，渲染出本地 `<audio>`；扬声器出声仍需真机
确认。

### T-092 把词典选择/查词结果放在 SearchPage/LookupSheet 的 State

**误区**：切换页面丢结果；两个界面选择不同步。

**正确做法**：选择与模式放全局 `lookupPreferencesProvider` 并持久化；查询词/结果
放 app-lifetime `lookupSearchProvider`。两个界面共用选择，切换页面不丢结果；
外部修改选择后已有查询要自动刷新。

### T-093 选中词典时改变字体粗细/宽度来强调

**误区**：Chip 尺寸变化导致 Wrap 重排、结果区上下抖动。

**正确做法**：只改背景/边框/文字色，保持同一字重和固定行高；否则 Wrap 会重新
换行，词典位置漂移并让结果区上下抖动。筛选条预留 3.5 行（第 4 行半可见），其余
在筛选条内部纵向滚动。

### T-094 继续用 SnackBar 显示“已保存”等轻提示

**误区**：底部气泡拦截其覆盖区域的点击。

**正确做法**：用根 Overlay 的 `RikaiToast` + `IgnorePointer`，否则底部气泡会拦截
其覆盖区域的点击。

### T-095 竖排页只跑 MangaOCR，或只用平均置信度决定引擎

**误区**：单引擎/单指标决策，错过更优的 Paddle 结果。

**正确做法**：同时跑 MangaOCR 与 PaddleOCR，用 `OcrTextQuality` 综合置信度、
假名覆盖、有效字符和重复噪声评分；Paddle 需明显胜出（分差 >0.04）才切换。最佳
主候选 <0.80 时才尝试 ±90° Paddle；真实图片扫描结果见
`docs/04-历史/阶段4.5状态.md`，旋转未胜出，所以不要无条件增加两轮旋转。最终只返回
一个引擎，手动 vertical 缺 Manga 仍报错。

### T-096 把 OCR 块之间的空格原样交给 UniDic

**误区**：日文之间残留空格，复合词被拆成单字。

**正确做法**：`composeOcrText` 去掉日文之间的空格和日文标点两侧空格，保留拉丁
词间空格和换行。否则 UniDic 会把复合词拆成单字。

### T-097 长分词结果用 `ListView(children: [...])` 或保留默认滚动条

**误区**：一次性构建全部 token；滚动条随行高抖动。

**正确做法**：用 `ListView.builder`/`SliverList.builder` 懒加载，并在这类变高
token 列表上用 `NoScrollbarBehavior`；默认滚动条的估算高度会随行高变化而抖动。

### T-098 批量导入扫描完后仍保留“应用会递归……”和“扫描完成”，挤压词典列表

**误区**：状态说明长期占用列表高度。

**正确做法**：说明只在结果列表为空时显示；探测完成把 `_status` 清空，把高度让给
`Expanded` 的词典列表。

### T-099 手动添加 MDict 对话框的路径输入框 `autofocus: true`

**误区**：打开对话框自动弹键盘，遮挡横屏内容。

**正确做法**：`autofocus: false`，打开对话框前后清理焦点；选择文件夹返回后再次
`unfocus`，避免键盘遮挡横屏对话框。

### T-100 把“每词典词条上限”的 5 个选项直接放进无滚动的 AlertDialog Column

**误区**：横屏/小屏无法滚动到“10 条”。

**正确做法**：`ConstrainedBox(maxHeight: screen.height * 0.55)` +
`SingleChildScrollView`，保证竖屏/横屏都能选到“10 条”。

### T-101 照片拖拽最小高度仍是 120dp，图片永远无法完全让位给结果

**误区**：照片区无法收起到 0，长结果没有足够空间。

**正确做法**：允许照片高度到 0；`PhotoPane` 在
`height <= captureResizeHandle` 时隐藏图片和 overlays，只渲染 40dp 拖拽条，
拖拽起点用有效高度，这样下拉可以连续恢复图片。照片集和语料详情共用该行为。

### T-102 查词筛选条继续显示“查询词典”标题行和模式切换

**误区**：筛选条占用额外高度；模式胶囊位置不符合页面规范。

**正确做法**：筛选条从 Chip 开始；模式胶囊放 SearchPage AppBar，或 LookupSheet
标题行与词条标题同 y 居中。选中态不得改变 Chip 宽度。

### T-103 阅读页隐藏工具栏后无法恢复，或恢复图标不在原 x 位置

**误区**：隐藏后没有恢复入口，或恢复图标位置跳动。

**正确做法**：分词结果出现后显示灰色“隐藏输入框”；隐藏时记录状态，在 AppBar
下方左侧用同 inset 的 visibility 图标恢复；隐藏期间结果列表占用全部剩余高度。

### T-104 UniDic 路径只能填精确目录

**误区**：用户选到父目录/含 `matrix.bin` 的目录时判定无效。

**正确做法**：`UnidicValidator.discover` 递归查找 `matrix.bin` 并只保留通过完整
校验的目录；一个有效自动使用，多个用字体选择式列表（最后文件夹名为标题、完整
路径为副标题）。不要信任未通过 validate 的 `matrix.bin`。

### T-105 OCR 模型目录选到 `paddle_v5` 就认为路径无效

**误区**：用户选到单模型子目录时拒绝。

**正确做法**：`OcrModelManager.resolveModelsRoot` 把 `paddle_v5`/`manga_ocr`/
`orientation` 或含单模型文件的目录解析回父级 models 根目录；再校验/迁移。

### T-106 照片集所有照片共用一个 OCR 模式

**误区**：切换模式/照片时触发其他照片重识别。

**正确做法**：`CapturePhoto.mode` 每张独立、默认 auto；照片集、保存、多选页、
缓存键全部用当前照片的 mode。切换照片不得触发其他模式照片重识别。

### T-107 OCR 进行中禁用所有照片操作

**误区**：OCR 期间不能删除/旋转，用户被迫等待。

**正确做法**：保存到语料库可继续禁用；但单张删除和多选删除必须可用，删除前先
取消 OCR。旋转锁只包住文件旋转和清缓存，完成后释放，允许连续打断 OCR。

### T-108 查词只有完全匹配

**误区**：缺少增量/前方/后方匹配入口。

**正确做法**：全局 `LookupMatchMode`（增量/完全/前方/后方）+ 标题栏书籍图标
菜单；所有查词/点词页面显示。前方用词典前缀索引，后缀/增量在 worker 扫描并
缓存 key 列表，每词典默认最多 50 个 fuzzy 结果；查词页增量模式输入 300ms 防抖
自动查询。

### T-109 查词搜索框在加载时换成小尺寸 spinner

**误区**：输入框高度变化，结果区抖动。

**正确做法**：空闲和查询中都使用同一个 IconButton 尺寸，只替换 icon；否则输入
框高度变化会让整个结果区抖动。

### T-110 AppBar 上的多选/单选沿用浅色主题

**误区**：深蓝顶栏上未选中文字/边框对比度不足。

**正确做法**：`DictionarySelectionModeToggle(onDark: true)` 未选中文字/边框为
白色，选中为白底深蓝字；弹层内用浅色版本。

### T-111 找不到 OCR 模型时显示底层文件错误

**误区**：向用户暴露文件系统异常，不给出下一步操作。

**正确做法**：结果区写“未找到可用的 OCR 模型”，并提示点击页面下方「模型设置」；
不要要求用户自己找模型文件。

### T-112 长分词列表卡顿只靠去掉滚动条

**误区**：保留每个 TokenChip 的 Material/InkWell 图层，滚动仍卡顿。

**正确做法**：懒加载 + 去滚动条 + 去掉每个 TokenChip 的 Material/InkWell；变高
列表滚动时仍会按估算范围补建行，TokenChip 图层越少越稳。

## 12. Agent v2 设计期（阶段 6）（T-113–T-120）

### T-113 把图片路径、文件名、base64 或 EXIF 放进 provider 请求

**误区**：provider 能推断本地文件信息，或请求体包含图片数据。

**正确做法**：OCR 只在端侧执行；provider 只收到不含路径的文本 JSON
（`{image_id, ocr_text}`）。当前没有模型工具或 `ocr.recognize` 工具面；测试捕获
请求体断言无图片/路径/base64。

### T-114 把 MDict 原始 HTML、MDD 图片/音频或完整词条发给模型

**误区**：原始词条内容进入 provider，泄露资源或引入注入面。

**正确做法**：用 `htmlToPlainText` + sanitizer 生成摘要（长度上限按当前预算
常量）；去路径、base64、MDD/MDX、音频/图片引用。完整词条只在用户点击 citation
时走现有 WebView，不进入 provider。

### T-115 让模型决定先查哪本词典、如何合并/重排结果

**误区**：词典顺序和证据合并由模型控制，破坏用户偏好。

**正确做法**：词典顺序唯一来源是 `DictionaryInfo.order`；编排器按该顺序预取并
排序证据，模型只看到 `source-N`。同一词条多词典命中分别保留，不合并。

### T-116 长文本直接截断后继续分析，或预算超限时静默丢弃内容

**误区**：用户不知道哪些内容未被分析。

**正确做法**：超过源文本预算先让用户选段；超预算设置 `truncated=true` 并在 UI
明示“未分析的部分不会出现在结果中”，不静默截断。

### T-117 词典熟悉档案未经用户确认就保存，或写进用户 UniDic/MDict 目录

**误区**：档案未经确认持久化；污染用户数据目录。

**正确做法**：只有“保存并信任”才写应用私有 SQLite；支持本次跳过/不再询问；
档案只存结构与短样例，按文件 stat + schema/prompt 版本失效。

### T-118 多个 OCR 版本自动选一个覆盖原文，或让模型直接改写 OCR 文本

**误区**：静默覆盖原文引用；模型猜测被当成事实。

**正确做法**：默认单版本；冲突时展示差异和依据，用户点“采用”才生成新
`SourceVersion(origin: dictionary_repair)`；模型建议必须带 citation 或标“模型
猜测”，不得覆盖原文引用。

### T-119 把 Agent 会话词典选择写回全局 `lookupPreferencesProvider`

**误区**：Agent 会话选择污染查词页/阅读弹层的全局偏好。

**正确做法**：会话选择初始继承全局后快照，只写会话表；查词页/阅读弹层继续用
全局偏好，互不影响。模式切换和词典选择只能由用户 UI 修改，模型无权改。

### T-120 信任模型自报的 `citations_used`/`literal`，或把未知 citation 当可点来源

**误区**：模型可以伪造引用汇总或原文；未知 citation 可导航。

**正确做法**：citation 只由 `CitationRegistry` 发放；`citations_used` 从各 claim
的 `citation_ids` 重新汇总；`literal` 由 quote 填充；伪造/越界只显示为普通文本，
不导航。原文 quote 必须通过 `analysis_text` substring 校验。

## 13. 语料 / 引导（阶段 5）（T-121–T-129）

### T-121 首次启动直接进入主页，或给旧用户也强制弹引导

**误区**：新安装没有引导；已配置 UniDic 的旧安装被重复打断。

**正确做法**：路由初始位置由 `onboardingCompleted` 决定；新安装进入
`/onboarding`，已有 UniDic 路径的旧安装视为已完成；设置页可复位并重新打开。
引导里的“跳过”必须可用，`开始使用` 需要先勾选许可确认。

### T-122 阅读页只能看不能保存，或保存文本时伪造照片路径

**误区**：`image_path` 写假路径，语料卡片渲染损坏图片。

**正确做法**：使用 `HistoryStore.saveText`，`image_path` 存空字符串；语料卡片/
详情对空路径显示「文本语料」占位和复制按钮，不渲染 `Image.file`。

### T-123 直接把照片原文件复制进语料，导致存储膨胀或方向错误

**误区**：语料图片未压缩/未校正 EXIF。

**正确做法**：`HistoryStore` 在保存时烘焙 EXIF、最长边限制 2048、JPEG 85；无法
解码的格式回退为原样复制，保存不能因转换失败而失败。

### T-124 自动保存每次 OCR/每次进页面都写一条

**误区**：缓存命中或页面重建重复写入语料。

**正确做法**：默认关闭；开启后仅在**新识别结果**时写入，并用
photo id + mode + text 做会话内去重；缓存命中不重复保存。

### T-125 清空语料只删数据库行，图片副本留在磁盘

**误区**：清空后磁盘占用不下降。

**正确做法**：`HistoryStore.clear` 同时删除所有 `image_path` 和 corpus/images
目录内的文件；设置/语料页二次确认后调用并 invalidate 列表。

### T-126 清缓存时删除用户词典或已安装模型

**误区**：把用户数据当缓存清理。

**正确做法**：设置里的“清除词典资源缓存”只删
`getApplicationCacheDirectory()/mdict` 并失效渲染 LRU；“清除模型缓存”只删
`.part`/`.importing`；用户词典/UniDic/已安装模型不得触碰。

### T-127 用 `SharedPreferences` 的无前缀 key 写测试

**误区**：`setMockInitialValues` key 不匹配，测试停在 `/onboarding`。

**正确做法**：`setMockInitialValues` 使用 `flutter.` 前缀（如
`flutter.app_onboarding_completed`）；现有 widget 测试必须显式种入已完成引导，
否则会停在 `/onboarding`。

### T-128 为桌面 SQLite 单测添加 `sqflite_common_ffi` dev 依赖

**误区**：为测试引入依赖，导致 Android 构建在 native-assets 阶段下载失败。

**表现**：`flutter build apk` 在 native-assets 阶段尝试从 GitHub 下载
`libsqlite3.*.android.so`，本机 GitHub 不可达，直接构建失败（即使只是 dev
dependency）。

**正确做法**：不要加入该依赖；HistoryStore 的测试只覆盖纯函数（图片压缩、
block JSON），UI 保存用 fake `HistoryStore`。若将来必须测数据库，先解决 sqlite3
的 no-download/system 配置并验证 Android 构建。

### T-129 debug/集成测试后直接 `flutter build apk --release`

**误区**：生成物仍包含 `integration_test`，release 编译失败。

**表现**：`GeneratedPluginRegistrant.java` 仍包含 `integration_test`，release
编译报 `パッケージdev.flutter.plugins.integration_testは存在しません`。

**正确做法**：先跑一次
`flutter build apk --release --target-platform android-arm64
--split-per-abi --config-only` 重新生成 release 注册文件，再跑正式 release
build；`flutter clean` 不一定能解决。不要改注册文件本身。

## 14. Agent 请求、覆盖审查、结果滚动与解释概率（T-130–T-137）

### T-130 模型偶尔直接返回 HTTP 400（请求格式/参数不合法）

**误区**：把所有 400 都归因于 `max_tokens` 过大，或反过来写死一个统一上限
（例如 8,192）。不同模型能力差异很大，deepseek-flash 的输出上限远高于 8,192；
盲目降额既解释不了错误，也可能截断结果。

**正确做法**：发送前只做结构/类型校验（`provider_payload.dart`）：model 非空；
丢弃空白 message；至少一条非 system；Anthropic 合并连续同 role；清理未配对
UTF-16 surrogate 和 C0 控制字符；`max_tokens` 必须是正整数。发生 400 时读取
provider 的真实 error body 并分类（上下文超限、输出参数不支持、reasoning/tool
参数不兼容、通用参数无效）；debug 只记录请求 shape（model/消息数/roles/字符数/
max_tokens 类型/stream），不记录正文/Key。不要用 UI 重试掩盖 400，也不要恢复
`temperature/top_p/top_k`、`response_format` 或 tools。

### T-131 每次运行都提示“覆盖审查不可用”

**误区**：把覆盖审查当成必需步骤；发送完整 input envelope（含全部 variants）和
完整 evidence JSON；一个 MISSING 项属性不合法就让整份 review 失败；只给一次修复
且输出预算过小；把空 sufficient 块缺少结束标签当成结构错误。

**正确做法**：覆盖审查是可选增强。输入改为紧凑投影（选中文本 + token/pattern id
+ 清洗 citation 摘要，保留 offset 与 entry_key/matched_key）；单项畸形只丢弃该项，
并记录每次自动修正的原值/修正值；空 sufficient/自闭合标签先规范化，修复请求使用
规范化后的文本（幂等）；输出预算由 `AgentLimits.coverageReviewMaxTokens` 按 MISSING/
duplicate 上限、reason 长度、标签开销和安全边际独立计算，系数/开销常量统一在
`AgentLimits.coverage*`（`coverageCharsPerToken=1.0`，CJK 保守），不跟随分析请求；
解析失败保留原证据并在 debug 记录脱敏原因。真实 provider 请求失败仍显示 warning，
不能伪装成审查成功。

### T-132 Agent 长结果下滑/展开依据词典时卡顿一次

**误区**：把长结果整棵 `Column` 一次性塞进展开的 `ExpansionTile`；每个段落/证据组
都启动一个 520ms 的 `TweenAnimationBuilder`；懒加载列表里的缩略图用
`Image.file` 全尺寸解码。结果展开或滚到依据词典时，一帧内完成大量 build/layout、
启动几十个动画或解码整张照片，表现为下滑中途卡顿一次。

**正确做法**：展开的详细解析按小块跨帧追加（`_ProgressiveResultBody`，首批 4 块、
之后每帧 3 块），每个词典依据组内的 citation 行也使用同一分块器；淡入只保留前
`AgentFadeIn.maxAnimatedItems` 个块，其余直接渲染。Agent 缩略图统一用
`agentThumbnailCacheSize` 计算 `cacheWidth`/`cacheHeight`，按显示尺寸解码。不要把
`ListView` 的 cacheExtent 当成修复；问题是一次构建量，不是预加载距离。语料详情页
的同类滚动问题另按该页的 sliver 分块策略处理。

### T-133 “可能的理解” A/B 都显示 70%，加起来 140%

**误区**：把每个 OPTION 的数字当成模型给出的独立概率；直接改 prompt 要求模型输出
概率或要求 A+B=100%。标签协议明确禁止模型输出 confidence/百分比，解析器只是给
OPTION 一个 0.5/0.7 的启发式相对权重；两个都带 citation 的选项自然都显示 70%。

**正确做法**：保持“模型不输出数值”，在管线里归一化。`normalizeAnalysis` 和
`salvageAnalysis` 在存在多个 OPTION 时按相对权重用最大余数法分配整数百分比，使总和
为 100%（两个 0.7 → 50%/50%；三个 → 34%/33%/33%）；只有一个 OPTION 时保留启发式
值。不要把这个展示约束写成 prompt 规则。新增/修改归一化逻辑时同时检查严格模式
salvage 删除选项后的二次归一化。

### T-134 推理模型只输出 reasoning_content、正文为空并重复请求

**误区**：给所有 OpenAI-compatible 请求固定填 `max_tokens=12000`，并假设越大越
安全；推理模型可能把预算全部消耗在隐藏 reasoning 上，SSE 结束时有
`reasoningChars` 但 `textChars=0`，provider 再走一次非流式 fallback，重复一遍长
推理，耗时翻倍。

**正确做法**：OpenAI-compatible payload 默认不发送 `max_tokens`，由服务端/模型
默认输出上限决定；provider 设置里可填可选 `maxOutputTokens`（设置页最后一个
输入框，OpenAI-compatible 建议留空），大于 0 时作为该服务的 `max_tokens` 发送。
Anthropic 仍必须发送，并优先 provider 值。解析 SSE 的
`finish_reason`；若 `textChars==0 && reasoningChars>0`，直接返回
`PROVIDER_EMPTY_OUTPUT`，不再发第二次请求，只有无 reasoning、无正文的真正空流才
fallback。日志记录 SSE 事件数、text/reasoning 字符数和 finish_reason。app 没有
reasoning-effort/thinking-off 参数；要真正缩短思考时间，应把复杂模型改成非推理
模型（如 deepseek-chat/flash）。流式进度更新节流（当前 250ms），避免上万 delta
触发大量 Riverpod 更新。

### T-135 富文本后处理标签导致原文被改动

**误区**：相信模型“只插标签”，直接渲染后处理输出；或只用长度/包含关系判断，
未逐字符校验。模型可能顺手改标点、删空格、改写词形，导致结果与已校验内容不一致。

**正确做法**：后处理只作用于详细解析的“原文”、逐句理解和词典事实解释（词义/语法，
不含 citation snippet）；AI 气泡摘要、可能的理解、未解决、模型补充、引用行和
词注/语法注 fallback 用本地 RUBY 渲染（不加载模型 BOLD/UNDERLINE），避免中文
译文被模型强调标签误标注；citation snippet 仍是词典原文。后处理只允许在原文之间插入 `[RUBY=reading]base[/RUBY]`、
`[BOLD]...[/BOLD]`、`[UNDERLINE]...[/UNDERLINE]`；注音由 AI 根据文本自身判断，
不读取 UniDic 读音表。结果生成模型会把 `[MEANING]` 和词条解释开头的读音标注成
`word[YOMI]reading[/YOMI]`（读音不带括号；单词=读音时只写单词）；普通括号
`（...）` 是解释性文字，不是读音。纯显示/导出读音使用 `reading【surface】`
（例如 `すき【好き】`，反向 `surface【reading】` 也接受）。后处理可以把整个 YOMI 块
（标签和读出内容）替换成等价 RUBY，但不得新增、改写、移动或嵌套 YOMI。代码必须先用
`stripRichTextTags` 剥离显示标签，按 YOMI 规则允许整块删除、要求保留块内容/位置
不变，再与原始字符串**逐字符严格比较**（不 trim、不做 Unicode 规范化）；只有完全
相等且标签成对、正确嵌套、RUBY 读音为安全发音标注（不限定书写系统）时才采用。
RUBY 可以位于 BOLD/UNDERLINE 内，BOLD/UNDERLINE 也可以相互包裹；BOLD/UNDERLINE
不得进入 RUBY 的 base，同一标签不得嵌套自身。每个 RUBY 的读音不得等于 base
（如 `[RUBY=reading]reading[/RUBY]`），这类冗余 RUBY 必须取消。YOMI 内容比较前要
清洗全角/半角标点；模型输出的 `[RUBY=内容]` 也要先清洗全角/半角标点，清洗后为空
或等于 base 时移除 RUBY。若后处理把已有的 `reading【surface】` 注记包进 RUBY，
显示必须折叠成一份读音：base 末尾与 RUBY 读音相同的读数会被隐藏，`[/RUBY]` 后
（即使隔着 `[/BOLD]`/`[/UNDERLINE]`）的相同读数会被本地转换删除；
`richTextToPlain` 输出 `reading【surface】`。模型若输出
`[BOLD]reading[/BOLD]【surface】`（或反向 `[BOLD]surface[/BOLD]【reading】`），
本地转换必须把读音移入强调 span 为
`[BOLD][RUBY=reading]surface[/RUBY][/BOLD]`，不能留下非粗体读数；
`[BOLD]reading【surface】[/BOLD]` 同样转 RUBY。普通括号不转换。RUBY 位于
BOLD 内时读音随 base 加粗；读音永远不加下划线（即使位于 UNDERLINE 内）；RUBY
base 使用与周围正文相同的行高/metrics，以 alphabetic baseline 对齐，不能把小字当作
基线而让 base 下沉。UNDERLINE 不要用 `TextStyle.decoration`（字体/字形 metrics
会让 `；` 与汉字的下划线高度不同），应使用 baseline 相对偏移的自绘线。保留的
YOMI 和 `reading【surface】` 读数在结果构建时本地转成 RUBY（预览首帧即可见）；
Markdown 导出用 `reading【surface】`。任何差异、未闭合/错误嵌套标签、空输出或 provider
失败都直接丢弃该块格式化结果，保留本地 RUBY 基线；不弹用户错误、不重试、不把失败输出交给
前端。Prompt 不得使用“uncertain 就返回原文”的模糊兜底；只允许不确定的具体词保持
原样。相关实现：`rich_text_post_processor.dart`、`rich_text_tags.dart`；契约
§5.3。内部 Prompt 指令统一英文，闭合标签统一用正斜杠 `[/TAG]`。

**2026-11-03 修正**：不再在调用后处理模型前把 YOMI 预转成 RUBY。模型输入保留
结果模型原始文本和 `word[YOMI]reading[/YOMI]`，prompt 也不再包含“保留已有
RUBY”“不要原样返回”“把 YOMI 转成 RUBY”三组规则，只保留标签格式、只插标签
不改字、合法嵌套。`reading【surface】` → `[RUBY=reading]surface[/RUBY]` 是
“不改字”规则的唯一例外，base 字符仍不得变化；普通括号 `（...）` 不是读数，
prompt 要求不转换。BOLD/UNDERLINE 内的读数必须
放在同一强调 span 内。本地 `localReadingsToRuby` 在 provisional/final/salvage 结果
构建时始终执行，预览首帧即 RUBY；provider/校验失败、模型保留 YOMI/`reading【surface】`
或某个 section 被拒绝时，同一转换兜底，模型格式化只追加 BOLD/UNDERLINE。预注入会让
轻量模型把格式化任务误解为改写任务，增加原样返回/非法输出。改动前的回归样本
读音/依据覆盖 9/9（100%），见 `docs/06-样本/` 与 `T-135` 相关记录。本地转换
识别 `reading【surface】` 和反向 `surface【reading】`（kana/Latin 侧视为读音）
并转成等价 RUBY；比较时把 `reading【surface】` 与
`[RUBY=reading]surface[/RUBY]` 归一化为同一 base，普通括号（解释性文字）不转换，
base 字符仍须完全一致。转换是标签感知的：BOLD/UNDERLINE 在读数前关闭时把读数
移入强调 span，RUBY 后（含隔着强调闭合标签）的重复读数删除。

### T-136 SSE 已收到 finish=stop，UI 仍等数秒才显示结果

**误区**：把“provider 日志出现 finish=stop/数据完整”当成“管线已经结束”。实际
可能还有三层等待：SSE socket 未关闭时 provider 继续 `await for`；首个分析已解析，
但 `done` 还在等格式修复、语言修复或富文本后置调用（各自是一次完整模型请求）；
进度节流器把最后一个 delta 丢弃。

**正确做法**：provider 在 `finish_reason`、`[DONE]`、`message_stop` 到达时立即
停止读取并取消订阅；`_collect` 把 `LlmEventType.done` 当终止事件。首个
parse/validate 完成后先通过 `onProvisionalResult` 渲染主结果（UI 显示“结果已出，
正在复核…”），不要等后置调用；修复阶段保持 `validating`。阶段切换时强制 flush
进度尾包。排查时看 debug 日志 `[AgentTiming]`（provider headers/first_event/
finish/stream_closed、stream label=...、stage、parse/validate/language、provisional、
controller、ui_result_frame）。不要在这条路径上同步等待 SQLite/文件写入；日志只
记录耗时/数量，禁止 prompt、citation、路径或 Key。相关实现：

### T-137 富文本批量请求中单个 section 损坏导致整批回退

**误区**：为了省调用，把“原文 + 逐句理解”合并成一个带 section marker 的请求后，
只要某个 marker 丢失/写错或某个 section 的 diff 失败，就 `return` 整批 local
fallback。用户会看到其他本来可以正常格式化的 section 也退回纯文本；省了成本，
却造成无故的显示质量下降。

**正确做法**：批量协议必须按 section 独立解析、独立校验、独立降级。

- 实现使用 `<<<RIKAI_SECTION id>>>` / `<<<RIKAI_END id>>>` 作为 section marker
  （概念上的 `[SECTION]`）；prompt 要求模型原样保留 marker。
- 按 id 逐个查找 open/close marker。某个 section 的 marker 缺失或损坏时，只把
  该 section 标为失败；继续从当前 cursor 搜索后续 section，不得 `return null`
  导致整批回退。
- 每个 section 单独执行 YOMI/标签完整性/`reading【surface】` 归一化/逐字符 diff。
  某个 section 的 diff 失败时只 `_localFallback` 该 section，其他 section 仍可
  采用模型输出。
- 只有 provider 错误、空响应、批量响应完全缺失 marker、总字符超过
  `maxRichTextChars` 等全局失败才允许整批回退；此时每个 section 都应保留本地
  RUBY 基线。
- 词注/词典事实解释不进入批量请求；仍由本地 `word[YOMI]reading[/YOMI]` /
  `reading【surface】` 转 RUBY。

参考实现：`rich_text_post_processor.dart` 的 `processSections`/`_splitSections`；
`agent_prompts.dart` 的 `buildBatchedRichTextPostProcessRequest`；契约 §5.3；
规则 `R-AGENT-LIMITS-001`。

### T-138 用 `NavigatorState.context` 弹 `RikaiToast`，toast 永远不显示

**误区**：`lookupAndOpenEntry` 在词典 `entry://` 跳转失败时用
`RikaiToast.show(navigator.context, ...)` 提示“当前词典中没有…”。查询确实
执行了（日志 `hits=0`），但页面没有任何提示。

**原因**：`RikaiToast.show` 通过 `Overlay.maybeOf(context, rootOverlay: true)`
向上查找 Overlay。`NavigatorState.context` 是 Navigator 本身的 context，位于它
创建的 Overlay **上层**；Overlay 是 Navigator 的子节点，因此向上查找返回 null，
`RikaiToast.show` 静默 `return`。`showDialog` 能工作是因为它直接由 Navigator
压入 overlay route，不依赖祖先 Overlay。

**正确做法**：

- 页面内 toast 使用页面/子树的 `BuildContext`（Overlay 的后代），不要传
  `navigator.context`。
- `RikaiToast.show` 增加兜底：祖先 Overlay 找不到时，若 context 的 State 是
  `NavigatorState`，使用 `state.overlay`；否则尝试
  `Navigator.maybeOf(context)?.overlay`。
- 回归测试直接以 `navigatorKey.currentState!.context` 调用 `RikaiToast.show`，
  断言消息可见。

参考实现：`lib/core/ui/rikai_toast.dart`、`lib/features/lookup/lookup_actions.dart`；
测试 `test/rikai_toast_test.dart`。

### T-139 依据卡片直接显示 MDict 内部 key

**误区**：Agent 依据卡片把 `LookupEntry.headword` 当标题直接渲染。明镜等词典的
entry key 是 `01570 03798`，大辞林重定向后是 `@daijirin2-...`，用户看到的是
无意义索引；点击后的词条页和复制 Markdown 也会带出同一串索引。

**原因**：MDict 的 key 只保证唯一和可定位，不保证可读；`LookupEntry` 的
`headword` 是最终解析 key，不一定等于词条内容里的标题。`matchedKey` 有时是
用户查询词，有时仍是内部索引，不能单独作为显示标题。

**正确做法**：

- 新增 `lib/core/utils/dictionary_entry_title.dart`：先清洗 HTML，取第一行
  内容的最简单词形式作为标题；`【...】` 仅作日语词典的兼容回退，避免把方框
  匹配当成多语种通用规则。再回退到 `headword/entry-title` 类元素和
  `matchedKey`；去除 `▽▼△▲` 等词典标记。
- `entryKey` 保留给查词、去重和 citation 导航；`AgentCitation.headword` 存
  显示标题。旧历史没有新标题时，从保存的 snippet 里提取 `【...】`。
- 所有用户可见面统一走 `citation.displayTitle`：依据卡片、语义标签、Markdown
  导出、fallback 弹窗、点击后的词条页、查词结果列表和 P6.6 依据预览。
- 不要用“是否含数字/字母”粗暴判断；`01570 03798`、`@daijirin2-...` 是索引，
  但 `apple`、`B2B` 是正常词条。

参考实现：`dictionary_entry_title.dart`、`AgentCitation.displayTitle`、
`evidence_builder.dart`；测试 `dictionary_entry_title_test.dart`、
`agent_result_view_test.dart`、`lookup_result_list_test.dart`。
