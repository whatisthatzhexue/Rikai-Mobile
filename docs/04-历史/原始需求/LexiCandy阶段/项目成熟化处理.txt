一、反思与调研
1.0离线版摘要（已过时）
核心问题/痛点：用户阅读日语原版书籍，或者在日本街头走动时，经常看到横写/竖写的日语句子。作为一名负责的日语学习者，很多人希望能通过手机拍照的形式，将这些原版语料留存下来。但每当用户需要学习其中各个单词时，总是需要特地跳转到EBPocket等专业mdict词典app，并且还需要自己人工识别图片上的文字。
本项目希望集成已经成熟的UniDic分词 + Mdict词典 + OCR，支持对用户照片OCR或接受用户输入的文本，处理时，先调用UniDic进行分词，然后对每个单词单元进行注音（同样依赖Mdict），用户点击单词单元，即可自动查询MDict。用户还可调整查询偏好，设置本次搜索选择哪些词典。除点击单词查词外，还支持基础的搜索查词功能。
本项目只负责加载以及分词逻辑，分词信息的提炼+词典的检索。旨在用一键化窗口的形式，帮助用户不必跳转多个app，就可以在一个窗口上离线学习日语。
为何已过时：极客工具走向参赛作品的必然方向转型和变化

新设计
本地优先、证据可追溯的 AI 日语精读工作台
传统语言 App 的漏斗是：下载 -> 打卡 -> 放弃。
为什么？因为它们只有‘学习’，没有‘消费与表达’。
而我们打造了一个‘阅读-输入-社区’的无缝飞轮。
用户用我们的 OCR 拍书精读（消费）；看到好的句子，想发表看法，但怕自己写错。没关系，我们用自研的纯 Flutter 键盘和 AI 教练，让他闭着眼睛都能写出地道的日语（生产）；写完带着 Diff 思考轨迹一键发到社区，收获同好的点赞（社交）。
我们不是逼着用户背单词，我们是为用户搭建了一个‘既能看懂世界，又能发出声音’的舞台。用户一旦用上，他的每一次输入、每一次纠错、每一次点赞，都沉淀在了我们的数据资产里。

竞品调查：Z次方输入法
产品优点：中文拼音输入法，输入中文，可在候选中文上方给出其正确的日语形式，支持变形后的动词，甚至支持短语。
锐评：交互体验比较差，字小，展开的候选中不显示日语对应词。并且不知道读音，信息过载，走马观花式学习。输入法功能存在学习成本，上下滑动太没有确定性容易误触。
核心矛盾：“输入效率”和“学习深度”不可兼得

我们做应用内输入法，而不做应用外的优势：APP内严格沙盒，不影响APP外输入法环境，又能让用户在应用内沉浸处理外语。
为什么不做输入法内长按显示词卡：会干扰用户的输出流，变为“查词流”
二、新技术设计
已确定端云相关内容
打开APP之后，应该先让用户看一些预存的电子书/示例图片，去看解析效果，然后引导用户去拍一张照片。
总领：注意隐私政策。这里主要是端云双层架构。
UniDic: 直接配布在服务端。通过服务端调用UniDic服务。License: GPL v2.0/LGPL v2.1/修正BSD （同时也支持用户使用自己的本地UniDic，作为兜底）
对于预存的电子书来说，直接预存UniDic分词结果，不依赖网络，离线就能看。
Mdict词典: 随apk包附带一个版权可行的小型MDict词典。用户还可以访问服务端上的MDict词典内容。同时也支持用户添加自己的本地MDict。
OCR: 对于预存的电子书来说，直接预存电子书内容，不需要OCR。做端侧OCR的模型选型+优化。在云端上做一个好一点的OCR模型。
Agent: 云端接API Key。本地接端侧小模型 + 可能的微调 + 架构优化。
这样做的好处：对于有网络的用户，开箱即可体验完整功能；若用户上飞机等无网环境，则可以将UniDic / MDict / OCR / 端侧小模型优先配置好，做到离线环境的最小学习环境。

插件系统实现抽象思路：
分词器抽象：确保你的 Token 数据模型（29 个字段）里的字段是可空（Nullable）的，英语不需要的字段留空即可。
词典检索抽象：MDict 的底层二进制解析（dict_reader）本身是跨语种的，但你要把“查询策略（Lookup Strategy）”独立出来。
日语策略：获取辞书形 -> 片假名/平假名互转 -> 匹配
英语策略：获取原形 -> 查大/小写形式 -> 匹配；获取词干 -> 查大/小写形式 -> 匹配
匹配步：用户可选择前缀匹配 后缀匹配 完全匹配 增量搜索 中的一个。
OCR 引擎抽象：定义 OcrRequest 接口，增加一个 Language 字段。日语走竖排/横排模型，英语走普通的文字行识别模型。你的 UI 层不需要知道底层调了哪个模型。
Agent 语言提示词抽象：在 agent_prompts.dart 里，按语言建立 Prompt 模板字典。日语系统 Prompt：强调注音、辞书形、助词。英语系统 Prompt：强调音标（IPA）、原形、短语动词（Phrasal Verbs）。
注意相同概念在不同语言下的不同解释：如日语/英语的时态的不同（日语为相对时态，英语为绝对时态）
重点：代码实现语言无关。新增语种只需添加路径 + 新增prompt。

Agent设计原则：
非必要少做主动式Agent（主动agent可能会在用户不感兴趣的地方偷偷吃预算）；被动式Agent需要用户最小决策（简化成按钮/备选问题之类的，尽量降低用户决策成本）
可一键询问，并且总是提供若干预制问题(除了与语境强相关的，都用mock预制问题兜底，然后才是Agent生成)给用户，减少不必要的打字输入。
Agent若提供给用户的输出无法在分词器或词典找到依据，必须标注内容为模型推断。
若能用“图 + 文”简易表现的，一般情况尽量设计相应的schema，而不是让用户看大段文字。
三、隐私相关
1. API Key 物理隔离：用户的云端大模型 Key 仅存在本地 Secure Storage，由手机直接连模型厂商。Python Worker 永远不接触、不代理用户的 Key。
2. 控制面与数据面分离：Worker 只负责下发最新的 Prompt 模板、规则配置（本地有兜底），实现“App 轻量化、规则云端化”。
3. 无感数据飞轮：在用户不知情（但隐私协议允许）的情况下，仅上报脱敏后的日活数据、解析失败率、词典未命中率。把用户当测试员，利用 Python Worker 自动聚类 Bad Case，用于后续 Prompt 优化和端侧小模型微调。
